# `packages/auth` — Authentication

Better Auth configuration shared between server and web. Owns the security policy for sign-in: which doors a deployment opens, the thresholds behind them, and the session cookie.

## Stack

- **Better Auth** — sessions, email/password, two-factor, one-time codes for address confirmation and password reset, OAuth and generic OpenID Connect.
- **`@better-auth/passkey`** — WebAuthn credentials, a primary sign-in method rather than a second factor.
- **Prisma adapter** — users, sessions, accounts, verifications, two-factor enrolments, passkeys and rate-limit counters stored in the shared PostgreSQL database.
- **`@freenary/email`** — the transport behind every code this package sends. It is a provider boundary; this package never talks to a mail service.

## Layout

```
src/
  cookies.ts        # resolveCookiePolicy() — SameSite/Secure from the origins + AUTH_COOKIE_DOMAIN
  emails.ts         # OTP subject/body copy, English only, sent through @freenary/email
  index.ts          # createAuth() + singleton export, plugin assembly, policy hook
  policy.ts         # thresholds (password, OTP, re-auth, rate limits) + the paths, code purposes and user fields refused
  providers.ts      # OAuth/OIDC providers read from the environment + authCapabilities
```

## Conventions

- `createAuth()` is the single source of truth for auth configuration. Both `apps/server` (handler) and `packages/api` (session resolution) consume it.
- **Thresholds live in `policy.ts`, never inline.** `MIN_PASSWORD_LENGTH`, `MAX_PASSWORD_LENGTH`, `OTP_*`, `SESSION_EXPIRY_SECONDS`, `TRUSTED_DEVICE_*`, `REAUTH_*` and the rate-limit rules are read by the server _and_ published to the interface, so a literal in two places is a drift bug waiting to happen. `packages/api` imports the module directly as `@freenary/auth/policy`.
- **A password is always the first factor,** and it takes three refusals rather than one. `emailAndPassword.enabled` is unconditional — there is no variable that disables it; `DISABLED_PATHS` refuses `/sign-in/email-otp` with `404`; `DISABLED_OTP_TYPES` refuses `type: "sign-in"` on `OTP_ISSUING_PATH` (`/email-otp/send-verification-otp`) with `400` / `INVALID_OTP_TYPE`, so the issuing route cannot be used as an unauthenticated mailer for a code nothing accepts; and `emailVerification.beforeEmailVerification` refuses a confirmation whose user is already `emailVerified` with `400` / `INVALID_OTP`, because `autoSignInAfterVerification` is on and that route otherwise mints a session past the password and the second factor. `emailOTP` is registered for address confirmation and password reset only; do not add a passwordless sign-in path back, and do not flip either verification flag without a design discussion first.
- **The plugin list is conditional on configuration, not minimal.** `buildPlugins()` always registers `twoFactor` and `passkey`, adds `emailOTP` only when `isEmailEnabled`, `genericOAuth` only when an OIDC provider is configured, and `haveIBeenPwned` only when `AUTH_PASSWORD_BREACH_CHECK` is on. A flow that cannot work is not registered, so it cannot be offered and fail.
- **The passkey relying party is derived from `CORS_ORIGIN`,** not from `BETTER_AUTH_URL` and not from a variable: WebAuthn binds a credential to the origin that created it, which is the web app. `rpID` is that URL's hostname and `origin` is the whole origin, which the plugin forwards to SimpleWebAuthn as `expectedOrigin` and which is compared by exact string — so changing `CORS_ORIGIN` invalidates every registered credential, a port change included. Do not introduce an override.
- **What the interface may offer comes from `authCapabilities`**, published by `packages/api`'s `auth.capabilities` procedure — never from build-time flags. It carries `emailDelivery`, `maxPasswordLength`, `minPasswordLength`, `oauth[]`, `otpLength`, `passkey` and `trustedDeviceDays`; `oauth[].id` crosses the boundary verbatim (`google`, `apple`, `oidc`) and `name` is an operator label — `OIDC_PROVIDER_NAME` or `null`, never a translated string and never the id, which the web app has its own message for. Adding a field here means adding it to `AuthCapabilities` too, and to the operator page.
- Environment variables come from `@freenary/env/server`: `BETTER_AUTH_SECRET`, `BETTER_AUTH_URL`, `CORS_ORIGIN`, `AUTH_COOKIE_DOMAIN`, `AUTH_PASSWORD_BREACH_CHECK`, `TRUSTED_PROXIES`, `GOOGLE_*`, `APPLE_*`, `OIDC_*`. Add new auth-related vars there, and keep `providers.ts` treating an unset credential as "provider off" rather than as an error.
- **Cookies are derived, not configured — with one declared fact.** `resolveCookiePolicy(authUrl, webOrigin, isProduction, cookieDomain)` gives `SameSite=Lax` for identical hostnames **or** a declared `AUTH_COOKIE_DOMAIN` (which also sets `advanced.crossSubDomainCookies`), and `None` otherwise, with `Secure` following the API's scheme. Four refusals throw: `None` over plain HTTP in production, and a declared domain that is not a parent of both hostnames, is a single label, or ends in a dot — browsers discard a cookie whose `Domain` they cannot match, so each has to fail loudly rather than as a sign-in that answers 200 and signs nobody in. Only the leading dot is normalized away, because that is the one RFC 6265 §5.2.3 ignores and the raw value is what reaches the browser. A multi-label public suffix such as `.co.uk` is knowingly undetected: a registrable domain cannot be derived from a hostname without a public-suffix list. Do not add a cookie override or guess the domain — change the origins or declare it.
- **Rate limits cap a caller only when the caller can be resolved.** Better Auth reads `x-forwarded-for` alone and refuses a multi-hop chain unless the hops are in `advanced.ipAddress.trustedProxies` (`TRUSTED_PROXIES`), keying everything else into one shared bucket per path — so an unset list caps the deployment rather than the caller. `@freenary/env` validates every entry as an address or CIDR range and refuses an IPv4-mapped IPv6 form outright, because Better Auth drops one it cannot parse and falls back to that shared bucket in silence. `packages/api`'s own limiter reuses that resolution through `getIP(headers, auth.options)`; never read forwarded headers by hand here or there.
- **One `hooks.before` hook, `enforceAuthPolicy`, enforces three policies.** Paths in `DISABLED_PATHS` answer `404`; `OTP_ISSUING_PATH` with a body `type` in `DISABLED_OTP_TYPES` answers `400` / `INVALID_OTP_TYPE`; `/link-social`, `/unlink-account`, `/passkey/delete-passkey` and both halves of passkey registration (`REAUTH_PATHS`) demand a session younger than `REAUTH_WINDOW_SECONDS` and answer `403` / `SESSION_NOT_FRESH` otherwise. The re-auth half exists because Better Auth guards unlink with `session.freshAge` but leaves link on a plain session check. `freshAge` is **raised** to `SESSION_EXPIRY_SECONDS`, not lowered to the window: it also gates `/list-sessions`, and freshness is measured from a session's `createdAt`, which never moves — so its 24-hour default made the active-sessions screen fail for six of the session's seven days. Never express "authenticated recently" through `freshAge`; it can only say "signed in recently". Raising it also made it inert on every route it gates — `/list-sessions`, `/unlink-account`, both halves of passkey registration, and `/delete-user` if it is ever enabled — so `REAUTH_PATHS` is the only protection left there. A new endpoint that changes which credentials open an account belongs in `REAUTH_PATHS` unless it already demands the account password — which is why the `/two-factor/*` endpoints are outside it, and why renaming a passkey is too; one the deployment does not offer belongs in `DISABLED_PATHS`; a code purpose it will not issue belongs in `DISABLED_OTP_TYPES`.
- Auth tables live in `packages/db/prisma/schema/auth.prisma`: `User`, `Session`, `Account`, `Verification`, `TwoFactor`, `RateLimit` and `Passkey`. `TwoFactor.secret` and `backupCodes` are encrypted with `BETTER_AUTH_SECRET`, `Passkey.publicKey` is public by construction, and rate-limit counters are persisted so a restart cannot clear a lockout.
- **A `User` column that only a Freenary procedure writes is `input: false` in `USER_ADDITIONAL_FIELDS`.** Better Auth copies every other declared field from the body of `/update-user` and `/sign-up/email` into the database, unvalidated. `onboardingCompletedAt` and `taxCountries` are written by `onboarding.completeOnboarding` alone, which enforces the bank precondition and the country list; with `input: false`, Better Auth answers `400` / `FIELD_NOT_ALLOWED` instead.
- Server-side email copy in `emails.ts` is **English only**: Paraglide's catalogs live in `apps/web` and the browser locale is not carried on an auth request. Do not reach for `m.*()` here.
- **Two-factor gates password sign-in; a passkey is a way in of its own.** Better Auth's plugin matches exactly `/sign-in/email`, `/sign-in/username` and `/sign-in/phone-number`, and `@better-auth/passkey`'s `/passkey/verify-authentication` creates a full session — so a passkey belongs with the sign-in options, never in the second-factor step. Enrolment needs the account password, so an account created through a connected provider cannot enable two-factor but can register a passkey. `trustDeviceMaxAge` is `TRUSTED_DEVICE_SECONDS` (30 days), and `trustDevice` rides on both `verifyTotp` and `verifyBackupCode`.
