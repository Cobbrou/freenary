---
title: Behind a reverse proxy
description: Put TLS and one or two public hostnames in front of the stack, and keep the session cookie alive.
icon: Network
---

Put a TLS terminator in front of the published ports. The simplest setup is one hostname for the web port, `3001` by default. A split setup sends a second hostname to the API port, `3000` by default.

TLS stops at your proxy. The stack declares no proxy service, no certificate volume and no port 443.

## The origins the proxy forces

A public hostname changes three values. You set two of them:

| Variable | What it must hold | Where you set it |
| --- | --- | --- |
| `BETTER_AUTH_URL` | The public URL of the API server | `.env` |
| `CORS_ORIGIN` | The public URL of the web app | `.env` |
| `PUBLIC_SERVER_URL` | The public URL of the API server, for the browser | Nowhere. Compose takes it from `BETTER_AUTH_URL` |

A `PUBLIC_SERVER_URL` line in `.env` is inert. The `server` service reads the whole file, and the `web` service reads no file at all.

Use `https://` in both values you set. The session cookie takes its `Secure` flag from the scheme of `BETTER_AUTH_URL`. `CORS_ORIGIN` must match the browser origin of the web app exactly. The API server allows that one origin for a cross-origin request. A value that does not match makes every sign-in fail.

[Configuration](/docs/self-hosting/configuration) defines each variable and quotes each refusal.

## What the browser receives, and what a change costs

The web app resolves the API origin at three points:

| Caller | Value it uses |
| --- | --- |
| The browser | `PUBLIC_SERVER_URL`, from an inline script in the root document |
| The web app itself, while it renders a page | `SERVER_URL`, which Compose sets to `http://server:3000` |
| Both, while the two above are unset | `VITE_SERVER_URL`, which Vite inlined at build time |

`PUBLIC_SERVER_URL` is a runtime value, so one image serves any deployment. A new public API origin therefore needs no new image. Change `BETTER_AUTH_URL`, then recreate the `web` service:

```bash
docker compose up -d web
```

The value must be an absolute URL. With anything else, every page answers `500`, and the web app throws `PUBLIC_SERVER_URL must be an absolute URL such as https://api.example.com, got "…"`. The web app cuts a slash at the end of the value.

<Callout type="info">

The web app calls `http://server:3000` on the Docker network while it renders a page. That call never leaves the host, so the proxy carries no server-side traffic.

</Callout>

## One hostname

One hostname can serve the whole instance. The web app forwards `/api/auth`, `/rpc`, `/ai/chat` and `/api-reference` to the API server, over the Docker network. Set both origins to the web app URL:

```dotenv
BETTER_AUTH_URL=https://freenary.example.com
CORS_ORIGIN=https://freenary.example.com
```

Send the hostname to the web port alone:

```text
freenary.example.com {
	reverse_proxy 127.0.0.1:3001
}
```

The browser then calls one origin. The session cookie stays `SameSite=Lax`, and `AUTH_COOKIE_DOMAIN` stays unset. Bind both ports to the loopback interface:

```dotenv
SERVER_PORT=127.0.0.1:3000
WEB_PORT=127.0.0.1:3001
```

The web app passes `X-Forwarded-For` to the API server unchanged. A caller that reaches port `3001` directly can write any address into that header. Each fake address then gets its own rate-limit bucket. The loopback binding lets only the proxy reach the port.

A hosting panel such as Dokploy or Coolify uses this setup with its own compose file. Read [Hosting panels](/docs/self-hosting/hosting-panels).

## Two subdomains

A split like `app.example.com` and `api.example.com` needs one more value. Set `AUTH_COOKIE_DOMAIN` to the parent domain both hostnames sit under:

```dotenv
AUTH_COOKIE_DOMAIN=.example.com
```

With it, the session cookie stays `SameSite=Lax` and carries `Domain=.example.com`. Without it, the cookie drops to `SameSite=None`, and a browser that blocks third-party cookies drops the session.

The API server refuses three shapes at startup, and each message names the value:

- A trailing dot, which browsers do not strip.
- A single label, which browsers treat as a public suffix.
- A domain that is not a parent of both hostnames.

A multi-label public suffix such as `.co.uk` is not detected. Declare the domain your two hostnames actually share.

<Callout type="warn">

Two different hostnames, no `AUTH_COOKIE_DOMAIN` and an API server on plain HTTP stop the start. The `server` container never becomes healthy. Compose always sets the production mode, so this check is always live. Serve the API over HTTPS, put both apps behind one hostname, or declare the shared parent domain.

</Callout>

[One hostname](#one-hostname) needs no cookie domain at all.

## Trusted proxies

Set `TRUSTED_PROXIES` to the addresses or CIDR ranges of every proxy in front of the API server:

```dotenv
TRUSTED_PROXIES=10.0.0.0/24,192.0.2.10
```

Each entry is one address or one CIDR range, in IPv4 or IPv6, and a comma separates the entries. An IPv4-mapped IPv6 address stops the start with `write an IPv4-mapped address in its IPv4 form, e.g. 10.0.0.0/24`. Write `10.0.0.1`, not `::ffff:10.0.0.1`.

The rate limiter keys each counter on the caller address. With an empty list and more than one address in the forwarded chain, the API server resolves no caller. One shared bucket then serves the whole instance, so one visitor can spend the sign-in allowance of every user. Read [Security](/docs/self-hosting/security).

## A worked example

This Caddyfile serves both hostnames, gets the certificates and forwards to the two published ports:

```text
api.example.com {
	reverse_proxy 127.0.0.1:3000
}

app.example.com {
	reverse_proxy 127.0.0.1:3001
}
```

The matching `.env` lines are these:

```dotenv
FREENARY_VERSION=main
POSTGRES_PASSWORD=<database password>
BETTER_AUTH_SECRET=<64 hex characters>
BETTER_AUTH_URL=https://api.example.com
CORS_ORIGIN=https://app.example.com
AUTH_COOKIE_DOMAIN=.example.com
```

Then check both hostnames from outside the host:

```bash
curl https://api.example.com/
curl -L -o /dev/null -w '%{http_code} %{url_effective}\n' https://app.example.com/
```

The API server answers `OK`. The web app sends a caller with no session to `/login`, so the second command prints `200 https://app.example.com/login`.
