Two commands answer most questions before you read further:

```bash
docker compose ps -a
docker compose logs --tail 100 server
```

## The image pull fails with `not found`

**What you see.** `docker compose pull` fails on both images, and the message names the tag.

**Why.** `FREENARY_VERSION` names a tag that the registry does not hold. A typo, or a `sha-` tag that predates the images, gives the same message.

**The fix.** Name a tag that exists in the root `.env` file:

```dotenv
FREENARY_VERSION=main
```

The tags are `X.Y.Z`, `X.Y`, `X`, `latest`, `main`, `dev` and `sha-<7 characters>`. [Updates](/docs/self-hosting/updates) lists what publishes each one.

## Compose creates no container at all

**What you see.** `docker compose up -d` starts nothing and prints one line. The line ends with the text from the compose file:

```text
Set POSTGRES_PASSWORD in .env
```

The same happens for `BETTER_AUTH_SECRET`. An absent file gives a message about a missing env file instead.

**Why.** `docker-compose.yml` marks both values as required. Compose stops before it creates anything when either one is unset or empty.

**The fix.** Write both in the root `.env` file, next to `docker-compose.yml`:

```dotenv
POSTGRES_PASSWORD=<from: openssl rand -hex 16>
BETTER_AUTH_SECRET=<from: openssl rand -hex 32>
```

**The check.** `docker compose config` prints the resolved stack. It fails with the same line while a required value is absent.

## The API server exits at startup

**What you see.** The `server` container never reaches `healthy`, and its log ends with a report:

```text
❌ Invalid environment variables: [
  {
    origin: "string",
    code: "invalid_format",
    format: "regex",
    pattern: "/^\\d+$/u",
    path: [ "PORT" ],
    message: "PORT must be a decimal number between 1 and 65535",
  }
]
error: Invalid environment variables
```

**Why.** One variable failed the schema. The `path` array names it, and `message` states what the schema wanted.

**The fix.** Correct that one variable, then recreate the service:

```bash
docker compose up -d server
docker compose logs -f server
```

An empty value counts as unset, so `PORT=` takes the default `3000`. A `BETTER_AUTH_SECRET` under 32 characters fails the same way. [Configuration](/docs/self-hosting/configuration) holds every schema and default.

<Callout type="error">

Do not set `SKIP_ENV_VALIDATION` to get past this report. The flag hides the mistake, and the server then runs on a broken configuration.

</Callout>

## The server does not restart after setup

**What you see.** After `Finish setup`, the setup screen waits for one minute, then shows `The server did not restart`.

**Why.** `Finish setup` stops the API server, so that it reads the saved configuration at the next start. A supervisor must start it again. The compose files set `restart: unless-stopped` for this. A server that runs with no supervisor, for example with `bun run dev`, stays stopped. A server that fails at startup also stays down.

**Fix.** Read the log of the server:

```bash
docker compose logs server
```

Correct the error that the log names, then start the server:

```bash
docker compose up -d server
```

Press `Try again` on the setup screen. It waits for the server again, and opens the app when the server is back.

## The server refuses a proxy address

**What you see.** The report above names `TRUSTED_PROXIES`, with this message:

```text
write an IPv4-mapped address in its IPv4 form, e.g. 10.0.0.0/24
```

**Why.** One entry holds an IPv4-mapped IPv6 address, such as `::ffff:10.0.0.1`. Better Auth drops such an entry and then treats the whole chain as unresolvable. The schema refuses it at startup instead.

**The fix.** Write the plain IPv4 form. The index in the `path` array names the entry to change:

```dotenv
TRUSTED_PROXIES=10.0.0.1,10.0.0.0/24
```

[Reverse proxy](/docs/self-hosting/reverse-proxy) shows how to write the whole list.

## The server refuses the email configuration

**What you see.** One of these two lines, and the process exits:

```text
EMAIL_PROVIDER=resend requires RESEND_API_KEY to be set.
EMAIL_PROVIDER=smtp requires SMTP_HOST to be set.
```

**Why.** A named adapter is half configured. Each line states the adapter you chose and the variable that adapter still needs.

**The fix.** Pick `resend` or `smtp`, and set every value that adapter needs. A stack missing both names `EMAIL_FROM` first, because the adapter checks it before its own values. [Email](/docs/self-hosting/email) holds both adapters.

## The server refuses the cookie domain

**What you see.** One of these three lines, with your own value in the brackets:

```text
AUTH_COOKIE_DOMAIN (.example.com.) ends in a dot, which browsers do not strip, so no host would match it. Drop the trailing dot.
AUTH_COOKIE_DOMAIN (.com) is a single label, which browsers treat as a public suffix and refuse to scope a cookie to. Declare the domain both origins sit under, e.g. ".example.com".
AUTH_COOKIE_DOMAIN (.other.com) is not a parent of both api.example.com and app.example.com, so browsers would drop the session cookie. Declare the domain both origins sit under, or leave it unset.
```

A fourth refusal names no variable, and it fires with `AUTH_COOKIE_DOMAIN` unset:

```text
The API (http://api.example.com) and the web app (https://app.example.com) are on different hosts, so the session cookie needs SameSite=None — which browsers reject over plain HTTP. Serve BETTER_AUTH_URL over HTTPS, put both behind one hostname, or set AUTH_COOKIE_DOMAIN to the parent domain they share.
```

**Why.** Each one describes a cookie no browser keeps. The server refuses at startup rather than answer `200` while nobody stays signed in. Outside production the fourth case is a warning that starts with `[auth]`.

**The fix.** Name the parent domain the two origins share, and serve the API over TLS:

```dotenv
BETTER_AUTH_URL=https://api.example.com
AUTH_COOKIE_DOMAIN=.example.com
```

A multi-label public suffix such as `.co.uk` passes all four checks, and no browser accepts it. Name the domain you own. [Reverse proxy](/docs/self-hosting/reverse-proxy) holds the split-host setup.

## The browser calls `http://localhost:3000`

**What you see.** The page loads on your real domain. The network panel of the browser shows calls to `http://localhost:3000/rpc`, and every one fails.

**Why.** The browser learns the API origin from `PUBLIC_SERVER_URL`. The `web` service takes that value from `BETTER_AUTH_URL`, which defaults to `http://localhost:3000`.

**The fix.** Set the real origin, then recreate both services. The web image needs no rebuild:

```dotenv
BETTER_AUTH_URL=https://api.example.com
```

```bash
docker compose up -d server web
```

Use `up -d`, and not `restart`. A restart keeps the environment the container got at creation.

**The check.** The root document must carry the origin before the module scripts:

```bash
curl -fsS https://app.example.com/ | grep __FREENARY_SERVER_URL__
```

A page that answers `500` holds a value that is not an absolute URL:

```text
PUBLIC_SERVER_URL must be an absolute URL such as https://api.example.com, got "api.example.com"
```

Write the scheme in front of the host.

## Every request fails with a CORS error

**What you see.** The web app renders, and every query fails. The browser console reports no `Access-Control-Allow-Origin` header on the answer.

**Why.** `CORS_ORIGIN` does not match the origin the browser loaded the web app from. That one variable is the whole allow list.

**The fix.** Set it, then recreate the API server:

```dotenv
CORS_ORIGIN=https://app.example.com
```

```bash
docker compose up -d server
```

Match the origin exactly: the same scheme, the same host and the same port, with no trailing slash.

## Sign-in works and the next request is anonymous

**What you see.** The sign-in call answers `200`. The next page load shows the sign-in screen again.

**Why.** The browser drops the session cookie. Three configurations cause it.

| Configuration | What the cookie gets |
| --- | --- |
| Two different host names, with `AUTH_COOKIE_DOMAIN` unset | `SameSite=None`, which a browser that blocks third-party cookies drops |
| `BETTER_AUTH_URL` on plain HTTP | No `Secure` flag, so the browser refuses the cookie |
| A browser that blocks all cookies for the site | Nothing. The screen reports that the browser kept no session |

**The fix.** Name the shared parent domain, and serve both origins over TLS. Read the section above on the cookie domain.

**The check.** Read the `Set-Cookie` header the server sends:

```bash
curl -isS -X POST https://api.example.com/api/auth/sign-in/email \
  -H 'Content-Type: application/json' \
  -d '{"email":"you@example.com","password":"your-password"}' | grep -i set-cookie
```

A correct answer names `__Secure-better-auth.session_token`, with `SameSite=Lax`, `Secure` and your `Domain`.

## No one-time code arrives

**What you see.** Sign-up or password reset asks for a 6-digit code, and no message arrives. Or the `Forgot password?` link is absent from the sign-in screen.

**Why.** The instance has no email adapter, so nothing sends a code.

| Cause | What you see |
| --- | --- |
| `EMAIL_PROVIDER` unset | No code, no address confirmation, and no `Forgot password?` link |
| A half-configured adapter | The server exits at startup and names the missing variable |

**The fix.** Set `EMAIL_PROVIDER` to `resend` or `smtp`, with the values that adapter needs. [Email](/docs/self-hosting/email) holds both.

**The check.** Read the server log after a start:

```bash
docker compose logs --tail 100 server
```

A running server holds a complete adapter, because a missing variable stops the process at startup. For a refused message the log holds the provider answer, such as `Resend rejected the message (403): <body>`.

## The stack stops because `migrate` failed

**What you see.** `docker compose up -d` ends with `dependency failed to start`, and it names the `migrate` container. The `server` and `web` containers never start.

**Why.** The `server` service waits for `migrate` to complete successfully, so a non-zero exit stops the whole start.

**The fix.** Read the exit code and the log of that one container:

```bash
docker compose ps -a
docker compose logs migrate
```

| What the log shows | Cause | Fix |
| --- | --- | --- |
| A failed connection to `postgres:5432` | The volume keeps the password of its first start, and `POSTGRES_PASSWORD` now holds another one | Put the first password back. A new one needs a dump, an empty volume and a restore |
| A failed SQL statement of one migration | The data in the database does not accept that migration | Restore your dump, then report the statement the log names |

Prisma records a failed migration in the `_prisma_migrations` table, and every later run stops at the same one. Read that state from the same image:

```bash
docker compose run --rm migrate bun x prisma migrate status
```

## The API answers `OK` and every data query fails

**What you see.** `GET /` answers `OK`, and every screen with data fails. The server log names a table that does not exist.

**Why.** The schema is behind the code. The one-shot `migrate` service never ran, or somebody started `server` on its own.

**The fix.** Bring the whole stack up, then read what `migrate` did:

```bash
docker compose up -d
docker compose logs migrate
```

The step is idempotent, so it is safe to repeat. The manual form works inside the API server container:

```bash
docker compose exec -w /app/packages/db server bun x prisma migrate deploy
```

## The bank list reports that linking is unavailable

**What you see.** Settings shows the empty state `Bank linking is unavailable`, with the text `This instance has no banking provider configured, so there is nothing to link against yet.` The bank list comes back empty.

**Why.** The credentials of the chosen provider are incomplete. Freenary checks them as a set.

| `BANKING_PROVIDER` | Needs all of |
| --- | --- |
| `powens` | `POWENS_DOMAIN`, `POWENS_CLIENT_ID`, `POWENS_CLIENT_SECRET` |
| `enable-banking` | `ENABLE_BANKING_APP_ID`, `ENABLE_BANKING_PRIVATE_KEY` |

**The fix.** Set every value of that provider, then recreate the API server:

```bash
docker compose up -d server
```

[Bank providers](/docs/self-hosting/bank-providers) covers both accounts and their redirect URLs.

## The bank section works and the list holds no bank

**What you see.** Settings shows the bank section, and the list of banks is empty. No message names a country, and the log holds nothing.

**Why.** Freenary read the credentials, so the section renders. The provider then answered with no institution for any jurisdiction of the profile. Two causes give that empty list:

| Cause | How to tell |
| --- | --- |
| The Powens domain activated no connector | The console lists the connectors of the domain as inactive |
| No jurisdiction of the profile has coverage | Another country fills the list |

A wrong domain makes the call fail instead. The list then reads `Freenary could not load banks for` and names those countries. A wrong client id or a wrong secret does not fail that call. The call for the bank list sends no token, and it reads only the domain. The list fills as usual, and the credentials stop the link later, when you select a bank.

**The fix.** Activate the connectors of the domain in the [Powens console](https://console.powens.com), then reload Settings. The server holds no institution cache, and it asks the provider on every call.

Freenary drops a connector that the provider marks `hidden` or `restricted`. It also drops one whose products name neither `bank` nor `wealth`.

## A bank link ends on an error page

**What you see.** The webview of the provider accepts the bank credentials. The browser then lands on an error of the provider. It can also land on a Freenary page that reports a failed link.

**Why.** The redirect URI of the client application does not match the one Freenary sends. Freenary builds it from `CORS_ORIGIN` and the callback path of the adapter.

| `BANKING_PROVIDER` | The URI to register                     |
| ------------------ | --------------------------------------- |
| `powens`           | `<CORS_ORIGIN>/callback/powens`         |
| `enable-banking`   | `<CORS_ORIGIN>/callback/enable-banking` |

**The fix.** Register that exact value at the provider. Powens accepts an HTTPS URI or an app scheme, so a `localhost` instance cannot finish a link. [Behind a reverse proxy](/docs/self-hosting/reverse-proxy) gives the web app a public origin.

## The assistant refuses every question

**What you see.** The assistant answers nothing. The screen reports `This instance has no model configured. An administrator sets AI_BASE_URL and AI_MODEL to switch the assistant on.`

**Why.** The chat route needs both values together. With either one absent it answers `503` with the body `unconfigured`.

**The fix.** Set both in the root `.env` file, then recreate the API server:

```dotenv
AI_BASE_URL=https://openrouter.ai/api/v1
AI_API_KEY=sk-...
AI_MODEL=anthropic/claude-3.5-sonnet
```

```bash
docker compose up -d server
```

**The check.** Read the two values inside the container:

```bash
docker compose exec server printenv AI_BASE_URL AI_MODEL
```

The chat route answers with a bare machine code on every failure.

| Status | Body | What it means |
| --- | --- | --- |
| `401` | `unauthorized` | The request carried no session |
| `503` | `unconfigured` | `AI_BASE_URL` or `AI_MODEL` did not reach the process |
| `429` | `rate_limited` | That account passed 30 questions in 300 seconds |
| `400` | `bad_request` | The body was not JSON |

[Assistant](/docs/self-hosting/assistant) covers the endpoints and what each question sends out.

## The wrong account became the operator

**What you see.** Your account opens `/setup` and reads `Only the operator can set up this instance`.

**Why.** Another account signed in to the instance before yours. The first account to sign in becomes the operator, and no screen moves the role.

An instance with accounts from an earlier release got its operator from the upgrade. The oldest account with a confirmed email address took the role, or the oldest account when none is confirmed.

**The fix.** When you made both accounts, move the role to your account. Put your email address in place of `you@example.com`:

```bash
docker compose exec -T postgres psql -U postgres -d freenary -c "UPDATE \"user\" SET role = CASE WHEN email = 'you@example.com' THEN 'OPERATOR'::\"UserRole\" ELSE 'MEMBER'::\"UserRole\" END;"
```

When a stranger made the first account, treat the instance as compromised. Stop it, remove the database volume, and install again before anybody else can reach it. [Security](/docs/self-hosting/security#the-operator) tells more.

## Every caller shares one rate-limit bucket

**What you see.** Users reach the rate-limit error after one try each. The problem follows the instance, and not one person.

**Why.** The caller address comes from the forwarded header. With `TRUSTED_PROXIES` unset, a header with more than one address resolves to nothing. Better Auth then keys every path on one shared literal, and the account-check limiter keys on `account-exists:untrusted`.

**The fix.** List every proxy in front of the API server, as an address or a range:

```dotenv
TRUSTED_PROXIES=10.0.0.0/24,192.0.2.10
```

```bash
docker compose up -d server
```

The counters live in the `rate_limit` table, so a restart clears no lockout. One statement clears them:

```bash
docker compose exec -T postgres psql -U postgres -d freenary -c 'DELETE FROM rate_limit;'
```

## Report a problem

Open an issue at [github.com/suiramdev/freenary/issues/new/choose](https://github.com/suiramdev/freenary/issues/new/choose). Blank issues are off, so pick one of the three forms: `Bug report`, `Feature request` or `Other`.

The bug form asks for two fields first.

| Field | What to put |
| --- | --- |
| Area | `Web app`, `Server / API`, `Database / migrations`, `Docker / local setup` or `Other` |
| Version or commit | The branch or commit you run, such as `main @ abc1234` |

Add these to the details, and your report needs no follow-up question:

- What you did, what you expected, and what happened.
- The exact error text, or the log lines around it.
- The output of `docker compose ps -a`.
- How you serve TLS, and which origins you set.
- The variables you set, with every secret removed.
