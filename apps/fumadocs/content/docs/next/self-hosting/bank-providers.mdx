Freenary never talks to a bank itself. A bank provider holds that connection, and `BANKING_PROVIDER` picks which one.

| Variable           | Default  | Accepted values            |
| ------------------ | -------- | -------------------------- |
| `BANKING_PROVIDER` | `powens` | `powens`, `enable-banking` |

An unknown value fails the environment check at startup. A known value with no credentials turns bank linking off rather than half on.

An operator sets the provider and its credentials in [the setup screen](/docs/self-hosting/setup), not only in `.env`. The screen calls the provider with the credentials before it saves them. A value already set in the environment wins, and the screen marks it read-only.

**Choose Powens unless you have a reason not to.** It is the default, and it is the only adapter that imports accounts, balances and holdings. [Powens](#powens) below walks the console setup step by step. A sandbox domain costs nothing and needs no contract.

## The two adapters

|  | Powens | Enable Banking |
| --- | --- | --- |
| Provider id | `powens` | `enable-banking` |
| Variables | `POWENS_DOMAIN`, `POWENS_CLIENT_ID`, `POWENS_CLIENT_SECRET`. All three | `ENABLE_BANKING_APP_ID`, `ENABLE_BANKING_PRIVATE_KEY`. Both |
| API host | `https://<POWENS_DOMAIN>.biapi.pro/2.0` | `https://api.enablebanking.com`, hard-coded |
| Consent screen | `https://webview.powens.com/connect` | the URL the provider returns |
| Callback path | `/callback/powens` | `/callback/enable-banking` |
| Consent window Freenary asks for | none. The provider and the bank decide | 90 days |
| Transactions | yes | yes |
| Accounts, account kind and balances | yes | **no** |
| Holdings on an investment account | yes | **no** |
| Bank name in the bank list | yes | yes |
| BIC, logo and bank group in the bank list | no | yes |
| Per-user identity at the provider | yes | no |
| Sandbox switch | none. The domain you were issued decides | none |

**Only Powens returns accounts, balances or holdings.** Enable Banking carries transactions and nothing else.

That split has three consequences on an Enable Banking instance:

- Every account keeps the kind `UNKNOWN`, because the link step writes no kind and no later call corrects it.
- Every balance column stays empty forever.
- Freenary asks for holdings on an investment account kind alone, so such an instance stores no holding.

An Enable Banking instance also never picks up an account that the user activated at the bank after the link.

<Callout type="info">

**No screen shows a holding or a balance.** A sync writes those rows, and no procedure reads them again. So the Powens capability changes what an instance stores, not what a user sees today. [Add a bank provider](/docs/contributing/bank-provider) holds the interface behind that.

</Callout>

**Country coverage.** Both adapters list banks per country, and the bank list is the answer of the provider. It is empty when the provider covers no bank in that country. Read the bank catalogue of the provider before you choose one.

### How Freenary picks the provider

`BANKING_PROVIDER` names the adapter that starts the **next** connection.

A connection that already exists remembers the adapter that created it. Freenary uses that adapter for every later sync, and for the disconnect.

So a change of the variable touches no existing connection. Both adapters can hold credentials at the same time, and that is the supported way to move. Set the new provider, keep the old credentials, and each user links the bank again when they choose.

## With no credentials

Nothing fails at startup. Every credential is optional, and `BANKING_PROVIDER` falls back to `powens`.

| Surface | What happens |
| --- | --- |
| Startup | The API server starts and signs users in as normal |
| The bank list | No screen asks for banks, because the availability check gates every bank surface |
| Settings | An empty block replaces the bank section |
| `/onboarding` | The bank step disappears, and the wizard finishes on the tax residency screen |

Settings reads:

```text
Bank linking is unavailable
This instance has no banking provider configured, so there is nothing to link against yet.
```

Freenary withholds that verdict until the check answers. A pending check shows a skeleton, and a failed check reads `Could not check bank linking` rather than a claim about the credentials.

<Callout type="warn">

A failed institution call is visible. The bank list names each country that Freenary could not load, and it keeps the banks of the other countries. An empty list with no such message means the provider holds no bank for those countries. Check the credentials and the provider host when the message appears.

</Callout>

## Powens

**Set up Powens.** It is the default of `BANKING_PROVIDER`, and the only adapter that imports accounts, balances and holdings. It also fills the Budget screen. No screen accepts a transaction by hand, so an instance with no bank provider shows nothing to budget.

Everything below happens in the [Powens console](https://console.powens.com). A sandbox domain is self-service and needs no contract.

<Callout type="warn">

**A redirect URI must use HTTPS, or an app scheme. Powens accepts no `http://localhost` URI.**

So the localhost stack of [Quickstart](/docs/quickstart) lists banks and finishes no link. The browser comes back to an origin the console refused to hold. Serve the web app over HTTPS first. [Behind a reverse proxy](/docs/self-hosting/reverse-proxy) holds that part.

</Callout>

<Steps>

<Step>

### Create the console account

[Sign up](https://console.powens.com/auth/register), then confirm your address from the email Powens sends.

The console asks for an organization next. It wants a company name, a company size, a country and an activity area.

</Step>

<Step>

### Create the domain

Choose a domain name. Powens creates it as a **sandbox** and appends `-sandbox.biapi.pro`, so the name `acme` gives the host `acme-sandbox.biapi.pro`.

A sandbox domain holds 50 connections. A production domain needs a signed contract, and your customer success manager at Powens opens it.

`POWENS_DOMAIN` takes the whole short name. For the example above that is `acme-sandbox`.

</Step>

<Step>

### Create the client application

Select the domain, open **Client Applications**, then add a client. Two fields matter: the name, which no user sees, and the redirect URIs.

Register this one redirect URI, and nothing else:

```text
<CORS_ORIGIN>/callback/powens
```

`CORS_ORIGIN` is the public origin of the web app. Freenary builds the redirect from it and from the callback path of the adapter. Powens then matches that value against the list you registered here. A value that differs by one character fails the link.

Note the client id and the client secret. They are `POWENS_CLIENT_ID` and `POWENS_CLIENT_SECRET`.

</Step>

<Step>

### Activate the connectors

A new domain carries no active connector. Open the product section you want, then activate each bank you want to offer, or activate all of them.

A domain with no active connector answers with an empty bank list. The instance then looks unconfigured while the credentials are correct.

</Step>

<Step>

### Write the three variables

```dotenv
BANKING_PROVIDER=powens
POWENS_DOMAIN=acme-sandbox
POWENS_CLIENT_ID=12345678
POWENS_CLIENT_SECRET=xxxxxxxxxxxxxxxxxxxxxxxx
```

All three `POWENS_` variables must hold a value. One empty variable turns Powens off, and no message says so.

Apply them to the running stack:

```bash
docker compose up -d
```

Compose recreates the `server` container with the new environment. No image rebuild is needed.

</Step>

<Step>

### Check that a bank reaches the list

Sign in, open **Settings**, then the `Connections` pane. It lists the banks that your domain activated for each jurisdiction of your profile.

A list that stays empty means the jurisdictions, the connectors or the credentials. `Bank linking is unavailable` in place of the section means Freenary read no credentials at all.

</Step>

</Steps>

**What `POWENS_DOMAIN` means.** Freenary trims the value, strips `.biapi.pro` from the end, then appends `.biapi.pro` again. So `acme-sandbox` and `acme-sandbox.biapi.pro` both give the host `acme-sandbox.biapi.pro`.

**Which banks reach the bank list.** Freenary drops a connector marked `hidden` or `restricted`. It keeps a connector whose products hold `bank` or `wealth`. Without the Wealth product the investment connectors drop out, and a bank connection still imports transactions.

**A first link without your own bank credentials.** Powens documents a test connector, `Connecteur de test`, on every domain. Any user name works there, and the password is `1234`. It reaches the Freenary bank list only while your domain leaves the connector visible.

**Webhooks are not needed.** The console offers them, and Freenary ships no webhook receiver, so a subscription changes nothing. Leave that step of the console onboarding empty.

**Per-user identity.** Powens mints one token per user at `POST /auth/init`. Freenary stores it in the `bank_provider_user` table and deletes the row when the user holds no Powens connection left.

## Enable Banking

Create the application in the [Enable Banking control panel](https://enablebanking.com/sign-in/).

<Steps>

<Step>

Register an **application**. Note its application id.

</Step>

<Step>

Download the **private key** of the application. Enable Banking hands it over once.

</Step>

<Step>

Register the redirect URL of the application, exactly `<CORS_ORIGIN>/callback/enable-banking`.

</Step>

</Steps>

```dotenv
BANKING_PROVIDER=enable-banking
ENABLE_BANKING_APP_ID=aaaaaaaa-bbbb-cccc-dddd-eeeeeeeeeeee
ENABLE_BANKING_PRIVATE_KEY="-----BEGIN PRIVATE KEY-----\nMIIEvQ...\n-----END PRIVATE KEY-----"
```

Both variables must hold a value. One empty variable turns Enable Banking off.

**How to write the private key.** Freenary turns every literal `\n` into a real newline before it signs. So the whole PEM fits on one line, as the fence above shows. A real multi-line PEM also works. Freenary supports no passphrase and checks no key format.

**The signature scheme.** Freenary mints a fresh JSON Web Token for every call and sends it as a bearer token.

| Part      | Value                    |
| --------- | ------------------------ |
| Algorithm | `RS256`                  |
| `kid`     | `ENABLE_BANKING_APP_ID`  |
| `aud`     | `api.enablebanking.com`  |
| `iss`     | `enablebanking.com`      |
| `sub`     | `ENABLE_BANKING_APP_ID`  |
| `exp`     | 3600 seconds after `iat` |

**The consent window.** Freenary asks for access until 90 days ahead. A bank can grant less. Freenary handles no shortened consent, so such a connection stops earlier than 90 days.

<Callout type="warn">

**Freenary stores the provider token in the database in plain text.** The Powens token per user sits in `bank_provider_user`, and the provider session id of a connection sits in `bank_connection`. Anybody with read access to the database can pull bank data through the provider.

</Callout>

## The connection lifecycle

| Step | What happens |
| --- | --- |
| Link | One database transaction writes the connection row and one account row per returned account |
| First sync | Freenary reads 90 days of history for each account |
| Later sync | Freenary resumes from the date of the last successful sync |
| Forced sync | Freenary reads the 90-day window again |
| Disconnect | Freenary asks the provider to revoke, then deletes the connection, its accounts, its transactions and its holdings |

**Freenary writes one connection status, and only one: `ACTIVE`.** The row takes it at creation, and no code path writes another value. A sync updates the last-sync date and nothing else.

A failure changes no status either. Powens can report that a connection needs the attention of the user. The adapter then throws, and the whole sync of that connection stops.

The message reaches the caller in the `error` field of the sync answer, and the status stays `ACTIVE`.

<Callout type="warn">

**There is no reconnect procedure and no reconnect button.** A connected bank row carries two actions: re-sync and disconnect.

A user whose consent ended therefore disconnects the bank and connects it again. That writes a **new** connection row, with new accounts and a fresh 90-day import.

</Callout>

Freenary also ships no scheduler and no webhook receiver. A consent change at the bank is invisible until the next sync a user starts. [Bank connections](/docs/guides/bank-connections) shows those actions from the side of the user. [Troubleshooting](/docs/self-hosting/troubleshooting) holds the failure list.

## The merchant dictionary

Freenary names a merchant from a prebuilt dictionary before it falls back to card codes and keyword rules. That dictionary is a build artifact, not a live service, so no transaction leaves the instance for it.

**What the weekly workflow publishes.** A GitHub Actions workflow runs each Monday at 03:00 UTC, and on demand. It builds the dictionary and attaches one asset, `merchant-data.tar.gz`, to a release tagged `data-<date>`.

| Member of the tarball       | When it is there           |
| --------------------------- | -------------------------- |
| `data/merchants.jsonl.gz`   | always                     |
| `data/place-tokens.json`    | always                     |
| `data/wikidata-brands.json` | when the build produced it |

**How an instance uses it.** The server image downloads the newest `data-` release at build time and unpacks it into the image. At run time the API server streams `data/merchants.jsonl.gz` line by line and matches a merchant key against it.

A missing file is not fatal. Freenary warns once with `Dictionary file not found` and leaves the dictionary stage empty. Every later stage still runs.

<Callout type="error">

**`DICTIONARY_PUBLIC_KEY` disables the dictionary.** The variable turns signature checks on, and the loader then demands `merchants.jsonl.gz.sig` beside the artifact. The published tarball packs no signature file at all.

So an operator who sets that variable on a stock image gets `Dictionary signature missing: <path> - refusing to load`, an empty dictionary and no error. Merchant names then come from the later stages alone.

Set the variable only against a dictionary you build and sign yourself. It is read straight from the environment and sits outside the validated schema, so nothing catches the mistake at startup.

</Callout>

[The categorisation pipeline](/docs/contributing/categorisation) holds the stages the dictionary feeds.
