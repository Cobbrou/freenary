A database dump plus the root `.env` file is the whole backup of a Freenary instance.

## One volume holds the state

`docker-compose.yml` declares one named volume, `freenary_postgres_data`, mounted at `/var/lib/postgresql` on the `postgres` service. Compose prefixes it with the project name `freenary`, so Docker reports it as `freenary_freenary_postgres_data`.

The `server`, `web` and `migrate` services declare no `volumes:` key at all. There is no second mount to forget.

| What | Where it lives | Back it up |
| --- | --- | --- |
| The whole database | The volume above | Yes, as a dump |
| The configuration and the secrets | The root `.env` file on the host | Yes, as a file copy |
| The merchant data of the categorisation stage | Inside the API server image, under `packages/api/data` | No. Each published image carries its own copy |

The development stack uses a different volume, `pgdata`, at the same container path. Docker reports it as `freenary-<slug>_pgdata`.

## Dump the database

The database is `freenary` and the role is `postgres`. Both are literal values in `docker-compose.yml`, and neither one reads a variable.

Take a custom-format dump. It compresses, and `pg_restore` can read it selectively:

```bash
docker compose exec -T postgres pg_dump -U postgres -d freenary -Fc > freenary.dump
```

Take a plain SQL dump instead when you want to read the file:

```bash
docker compose exec -T postgres pg_dump -U postgres -d freenary > freenary.sql
```

| Format    | Flag  | Restore with |
| --------- | ----- | ------------ |
| Custom    | `-Fc` | `pg_restore` |
| Plain SQL | none  | `psql`       |

<Callout type="warn">

Use `exec -T`, and never plain `exec`. Docker attaches a terminal without that flag, and the terminal corrupts the bytes of a custom-format dump.

</Callout>

Copy the root `.env` file next to the dump in the same step:

```bash
cp .env "freenary-env-$(date -u +%Y-%m-%d).bak"
```

The stack also publishes PostgreSQL on the host loopback interface, at `POSTGRES_PORT`, which defaults to `5432`. A host tool can therefore dump the database directly. The host `pg_dump` must be version 18 or newer:

```bash
pg_dump "postgresql://postgres:<database-password>@localhost:5432/freenary" -Fc > freenary.dump
```

## Restore

Stop the two apps first. An open connection blocks the restore, and a half-restored database answers wrong.

<Steps>

<Step>

### Stop the web app and the API server

```bash
docker compose stop web server
```

Leave `postgres` up. The next commands run inside that container.

</Step>

<Step>

### Restore the dump

`pg_restore` drops each object before it creates it again:

```bash
docker compose exec -T postgres pg_restore -U postgres -d freenary --clean --if-exists < freenary.dump
```

A plain SQL dump drops nothing, so start from an empty database:

```bash
docker compose exec -T postgres dropdb -U postgres freenary
docker compose exec -T postgres createdb -U postgres -O postgres freenary
docker compose exec -T postgres psql -U postgres -d freenary < freenary.sql
```

</Step>

<Step>

### Add the `citext` extension if the restore asks for it

The schema declares the PostgreSQL extension `citext`, and one column uses that type. A full dump carries the `CREATE EXTENSION` statement, so a plain restore adds it. Add it by hand when the restore names it as missing:

```bash
docker compose exec -T postgres psql -U postgres -d freenary -c 'CREATE EXTENSION IF NOT EXISTS citext;'
```

The first migration holds the same statement, so a start against an empty database also creates it.

</Step>

<Step>

### Start the stack again

```bash
docker compose up -d
docker compose ps -a
```

The `migrate` service runs before the API server. It applies every migration the restored database does not hold. A dump from the version you run now needs none, and `migrate` exits `0`.

</Step>

</Steps>

## Check that the data came back

Count the rows of two tables a live instance fills. SQL reads `user` and `transaction` as keywords, so quote each name:

```bash
docker compose exec -T postgres psql -U postgres -d freenary -c 'SELECT count(*) FROM "user";'
docker compose exec -T postgres psql -U postgres -d freenary -c 'SELECT count(*) FROM "transaction";'
```

A `user` count of `0` means the restore hit the wrong database. Then sign in and open a page that lists transactions. A successful sign-in proves two more things: the session rows came back, and `BETTER_AUTH_SECRET` still matches the data.

## Prove a dump restores, on a throwaway stack

Do this twice a year, and after any change to the backup command. Compose runs a second, separate stack from the same file when you pass a different project name. That stack gets its own volume and touches nothing of the live one.

<Steps>

<Step>

### Start a scratch database on another port

```bash
POSTGRES_PORT=5433 docker compose -p freenary-restore-check up -d postgres
```

The project name creates the volume `freenary-restore-check_freenary_postgres_data`. The port override keeps the live stack on `5432`.

</Step>

<Step>

### Restore the dump into it

```bash
docker compose -p freenary-restore-check exec -T postgres \
  pg_restore -U postgres -d freenary --clean --if-exists < freenary.dump
```

</Step>

<Step>

### Count the same two tables

```bash
docker compose -p freenary-restore-check exec -T postgres \
  psql -U postgres -d freenary -c 'SELECT count(*) FROM "user";'
docker compose -p freenary-restore-check exec -T postgres \
  psql -U postgres -d freenary -c 'SELECT count(*) FROM "transaction";'
```

Each count must match the live stack. A mismatch on either one means the dump is not complete.

</Step>

<Step>

### Delete the scratch stack

```bash
docker compose -p freenary-restore-check down -v
```

</Step>

</Steps>

<Callout type="error">

Type the `-p freenary-restore-check` flag in the `down -v` command. Without it, the flag deletes the volume of your live instance.

</Callout>

## What a dump does not hold

A dump holds what [the setup screen](/docs/self-hosting/setup) saved. It holds nothing from the `.env` file, which sits on the host next to `docker-compose.yml`. It is outside every volume, and `.dockerignore` keeps every `.env` file out of the image layers.

| Not in the dump | What you lose without it |
| --- | --- |
| `BETTER_AUTH_SECRET` | Every session, every two-factor enrolment, and every row of `instance_setting` |
| `POSTGRES_PASSWORD` | Access to the volume the old container created with it |
| A provider credential set in `.env` | The bank sync, or the one-time code delivery, of that adapter |

The `instance_setting` table is in the dump. A provider credential typed into the setup screen therefore comes back with the data. Each row is sealed with a key made from `BETTER_AUTH_SECRET`, and opens under that secret alone.

<Callout type="error">

Keep `BETTER_AUTH_SECRET` with the dump. That one value signs the session cookie, and it encrypts the `secret` and `backupCodes` columns of the `two_factor` table. It also seals every `instance_setting` row, and signs the bank connection state that round-trips through the provider. A restore under a new secret signs every user out and breaks every two-factor enrolment. It also turns off every provider the setup screen configured.

</Callout>

Freenary runs no scheduler, so it takes no backup for you. Put the dump command in your own scheduler. Read [Maintenance](/docs/self-hosting/maintenance).
