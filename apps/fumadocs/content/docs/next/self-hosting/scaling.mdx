Two questions decide how far one instance goes: what holds state, and what grows with use. This page answers both from the code of the stack. Every statement below describes the stack as it stands.

## What holds state

| Service | State it holds |
| --- | --- |
| `postgres` | All of it. One named volume, `freenary_postgres_data`, at the container path `/var/lib/postgresql`. |
| `server` | None on disk. Two read-only caches in memory. |
| `web` | None. |
| `migrate` | None. It runs one command and exits. |

`server`, `web` and `migrate` declare no `volumes:` key at all, so no second mount exists.

Two pieces of shared state matter for a second API replica, and both live in PostgreSQL:

| Shared state | Where it lives |
| --- | --- |
| Sessions | The `session` table, through the Prisma adapter. No secondary storage and no cookie cache are configured, so every request reads the row. |
| Rate limits | The `rate_limit` table. Better Auth writes counters there, and the oRPC limiter writes to the same table with one atomic statement. |

A second replica therefore reads the same sessions and counts into the same limit rows. A restart clears no lockout, because the counters are on disk.

## The in-process state that exists

The API server keeps one module-global cache. It holds read-only data that comes from the image:

| Cache                   | Source file in the image               |
| ----------------------- | -------------------------------------- |
| The merchant dictionary | `packages/api/data/merchants.jsonl.gz` |

A second replica duplicates that memory. It cannot diverge from the first, because both load the same file from the same image. Each replica releases the dictionary when its reference count reaches zero.

Each replica also reads the values of [the setup screen](/docs/self-hosting/setup) one time, at startup. Two replicas can therefore hold different values. [Settings from the setup screen](#settings-from-the-setup-screen) tells how to keep them equal.

Nothing else on the request path is mutable. The API server builds a fresh context for each request, and the auth middleware keeps nothing between calls.

## What the stack does not hold

Each fact below supports a second API replica:

| Fact about the code | Consequence |
| --- | --- |
| No background worker and no queue. No queue library and no Redis appear in any manifest. | Long work runs inside the request that asked for it. One bank sync loops over the connections in its own handler, with sequential provider calls. |
| No scheduler and no cron. The API server sets one timer: after `Finish setup`, it stops its own process. The web app sets one interface timer in a development-only route. | Nothing fires on its own, so two replicas cannot duplicate a job. |
| No external cache. Better Auth declares no `secondaryStorage`. | Sessions and counters go to PostgreSQL, which both replicas share. |
| No uploaded file on local disk. The whole HTTP surface is five route groups, and the server writes nothing to disk in production. | No replica holds a file the other one needs. |

Neither compose file declares `deploy.replicas`, a load balancer or a proxy service. A second replica is therefore your own composition. The code contradicts none of it, and the stack configures none of it.

## Settings from the setup screen

`Finish setup` restarts only the replica that answers it. Every other replica keeps the values it read at startup. Restart each other replica after `Finish setup`, so that all of them use the new values.

The setup screen waits for the restarted server before it opens the app. With more than one replica, it can ask a replica that did not restart. It then shows `The server did not restart`. Restart every replica, then press `Try again`.

## Connection pools

Each API replica constructs two Prisma clients: the module-level default client, and a second client inside the auth factory. Each client opens its own `pg` pool.

| Question | Answer from the code |
| --- | --- |
| How many pools does one replica open? | Two. |
| What pool size do they use? | The `pg` library defaults. The client factory passes a connection string and nothing else. |
| What does PostgreSQL allow? | The `max_connections` default of the `postgres:18` image. The compose file sets no `command:`, and the repository holds no `postgresql.conf`. |
| Where can you set a pool size? | In the `DATABASE_URL` query string. No file in the repository sets one. |

Watch the PostgreSQL connection count for that reason. Each replica you add multiplies it by two pools.

## Limits, restart policy and health checks

| Setting | What the production compose file declares |
| --- | --- |
| Resource limits | None. Neither compose file declares `deploy`, `mem_limit`, `cpus`, `pids_limit` or `ulimits`. |
| Log rotation | None. Neither file declares a `logging:` driver, so the Docker default applies and container output has no bound. |
| Restart policy | `unless-stopped` on `postgres`, `server` and `web`. `migrate` declares none, because it is one command that ends. |
| Health checks | On `postgres`, `server` and `web`: a 10 second interval, a 5 second timeout and 5 retries. Both apps add a 10 second start period. No Dockerfile declares a `HEALTHCHECK`. |
| Signals | `init: true` on `server` and `web` reaps the child processes. The API server registers no `SIGTERM` handler of its own, so it stops on the Docker default signal. |

To cap a service, put the limits on it in your copy of `docker-compose.yml`:

```yaml
services:
  server:
    deploy:
      resources:
        limits:
          cpus: "1.0"
          memory: 1g
```

## What grows with use

| Cost | What drives it |
| --- | --- |
| The database volume | Transactions per connected bank account. Each account adds its history, and the history only grows. Accounts, bank connections, categories and assistant transcripts share the same volume. |
| The model endpoint | Each assistant question calls it. The cap is 30 questions per 300 seconds per user. Read [Assistant](/docs/self-hosting/assistant). |

The merchant data is not state. The build writes it into the server image, and the server never writes it at runtime. An image update replaces it.

`freenary_postgres_data` is the one volume to size, and the one volume to back up. Read [Backup and restore](/docs/self-hosting/backup-and-restore).

## What to measure

The stack exposes no metrics endpoint and no exporter. These three numbers come from PostgreSQL, from Docker and from the logs:

| Number | Where to read it | Why it matters |
| --- | --- | --- |
| The PostgreSQL connection count | `pg_stat_activity` on the database | Each API replica opens two pools at library defaults, against the image default `max_connections`. |
| The size of `freenary_postgres_data` | `docker system df -v` | It is the only state on disk, and it only grows. |
| The API response codes | The `server` container output | The API server logs one wide event per HTTP request. Read [Logs](/docs/self-hosting/logs). |
