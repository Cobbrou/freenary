Freenary holds the bank data of every user. Two jobs are yours: the network edge and the secrets.

## What the stack publishes

| Service | Published port | Interface |
| --- | --- | --- |
| `server` | `${SERVER_PORT:-3000}:3000` | Every interface of the host |
| `web` | `${WEB_PORT:-3001}:3001` | Every interface of the host |
| `postgres` | `127.0.0.1:${POSTGRES_PORT:-5432}:5432` | The loopback interface alone |
| `migrate` | none | It publishes nothing |

The database mapping exists for host tools such as `pg_dump`, and it reaches no other machine. Delete the whole `ports:` block of the `postgres` service when no host tool needs it. The other services reach the database over the compose network.

The two application ports carry no loopback prefix, so both face every network the host is on.

<Callout type="warn">

Publish no application port to the internet. Add a `127.0.0.1` prefix to both application mappings, and point your reverse proxy at the loopback interface.

</Callout>

## What a reverse proxy must do

The API server listens on port 3000 and the web app on port 3001, both over plain HTTP. Neither app handles TLS. The stack holds no proxy service, no certificate volume and no port 443.

So a TLS reverse proxy in front of both apps is not optional for a served instance. It must also do two more things:

- Forward the real caller address, so the rate limits key on one user and not on the whole instance.
- Send the browser to origins that both start with `https://`. The session cookie takes its `Secure` flag from `BETTER_AUTH_URL`.

[Reverse proxy](/docs/self-hosting/reverse-proxy) holds the whole setup, the TLS rules and the trusted-proxy list.

## The container user

No Dockerfile in the repository sets a `USER` instruction, and neither compose file sets a `user:` key. The user each container runs as is therefore the default of the base image.

## The secrets

| Secret | Rule | What it protects |
| --- | --- | --- |
| `BETTER_AUTH_SECRET` | 32 characters or more | The session cookie, the two-factor data, the bank connection state, every `instance_setting` row |
| `POSTGRES_PASSWORD` | No default in the stack | The database itself, and the volume that holds it |
| The bank provider credentials | Set as a pair or a triple | The bank connection of every user |
| The email provider key | One key per adapter | One-time code delivery, and password reset |
| `AI_API_KEY` | Optional | Your account at the model endpoint |

Generate the two required values:

```bash
openssl rand -hex 16   # POSTGRES_PASSWORD
openssl rand -hex 32   # BETTER_AUTH_SECRET
```

`docker compose up` stops before it creates a container when either value is unset or empty. So every Docker instance holds two values you chose.

## The operator

The first account that signs in to a new instance becomes the operator. One database transaction gives the role, so two sign-ins at the same time cannot both get it.

A new instance on a public origin is open to anybody who finds it. If a stranger signs in first, that stranger becomes the operator. Create the first account in the same sitting as the install.

| Rule | Detail |
| --- | --- |
| Who becomes the operator | The account of the first session on the instance |
| An instance with accounts from an earlier release | The oldest account becomes the operator |
| How many operators | One. No screen and no endpoint grants the role a second time |

The operator role opens `/setup` alone. It grants no access to the rows of another user.

<Callout type="warn">

The schema default of `BETTER_AUTH_SECRET` is the literal `dev_secret_change_me_at_least_32chars`. It is 37 characters long, so it passes validation, and no production check refuses it. The Docker stack never reaches that default. A process started outside the stack does, and anyone can then forge a session cookie against it.

</Callout>

### What a rotation costs

| Rotate | What it costs |
| --- | --- |
| `BETTER_AUTH_SECRET` | Every user signs out. Every two-factor enrolment stops, and each user enrols again. A bank connection in flight fails at the callback |
| `POSTGRES_PASSWORD` | The volume keeps the password of its first start. A new one needs a dump, an empty volume and a restore |
| A provider credential | Rotate it at the provider, write the new value, then run `docker compose up -d server` |

Plan a rotation of the auth secret, and tell your users before you do it. Read [Backup and restore](/docs/self-hosting/backup-and-restore) for the dump the database password needs.

## The auth levers you control

Each lever below is on, off or absent because of your configuration. [Authentication](/docs/self-hosting/authentication) holds the variable and the exact rule for each one.

| Lever | State on a fresh instance | What turns it on |
| --- | --- | --- |
| Email verification | Off | An email provider. A new account then confirms the address with a code |
| Password reset | Off | The same email provider |
| Two-factor codes | On, per account | Nothing. Each user enrols in Settings, and an account with no password cannot |
| Passkeys | On | Nothing. The relying party comes from `CORS_ORIGIN` |
| The password breach check | On | `AUTH_PASSWORD_BREACH_CHECK` holds `true` by default |
| Google, Apple or single sign-on | Off | Both variables of that provider |
| Correct rate-limit buckets | Broken behind a proxy | `TRUSTED_PROXIES`, with every proxy address |

Four rules need no configuration at all, and no variable turns them off:

- A password holds 12 to 128 characters, and the server hashes it with scrypt.
- Ten wrong second-factor codes in a row lock that account for 900 seconds.
- Five account paths refuse a session older than 15 minutes, such as a passkey removal.
- The rate-limit counters live in a database table, so a restart clears no lockout.

<Callout type="warn">

The breach check fails closed. An instance with no route to `api.pwnedpasswords.com` cannot complete a sign-up or a password reset. Set `AUTH_PASSWORD_BREACH_CHECK=false` on an air-gapped host.

</Callout>

## The assistant sends financial data out

With a model endpoint configured, each question sends financial data of that user to the endpoint you named. That endpoint is a second party, under its own terms and its own jurisdiction. [Assistant](/docs/self-hosting/assistant) states what each question carries and what it never carries. Make the choice of endpoint before you open the assistant to real users.

## What the database holds

The database holds the accounts, the balances, the transactions and the holdings of every user. It also holds the bank provider access token of each user, in the `accessToken` column of `bank_provider_user`. The token sits there as it came from the provider. Anyone who reads that column can call the bank provider as that user.

<Callout type="warn">

Treat the database and every dump of it as the financial data itself. Encrypt the dump files, limit who can read them, and store them apart from the instance.

</Callout>

Freenary enables no account deletion. No screen and no endpoint removes a user. An operator who must erase one person does it in the database. A user can delete a bank connection, and that delete removes its accounts, transactions and holdings through the database cascade.

One role exists, and it is the operator. It opens the setup screen and changes the provider settings of the instance. It reads no financial row of another user, and every signed-in account otherwise reaches its own rows alone.

The `instance_setting` table holds the provider credentials the operator typed. Each row is sealed with AES-256-GCM, under a key made from `BETTER_AUTH_SECRET`. A reader of the table alone gets ciphertext.

## The checklist

Work through each line before real users arrive.

- [ ] `BETTER_AUTH_SECRET` holds your own value of 32 characters or more.
- [ ] `POSTGRES_PASSWORD` holds your own value.
- [ ] `BETTER_AUTH_URL` and `CORS_ORIGIN` name the real public origins, both over `https`.
- [ ] A TLS reverse proxy fronts both apps.
- [ ] No application port faces the internet.
- [ ] The `postgres` service publishes nothing, or it publishes to `127.0.0.1` alone.
- [ ] `TRUSTED_PROXIES` lists every proxy in front of the API server.
- [ ] `AUTH_COOKIE_DOMAIN` names the shared parent domain, for two subdomains.
- [ ] Your own account is the operator, so `/setup` refuses everybody else.
- [ ] The email provider is `resend` or `smtp`, so password reset works.
- [ ] `docker compose ps -a` shows `migrate` as `Exited (0)` and the rest as `healthy`.
- [ ] You know which endpoint `AI_BASE_URL` names, or you left it unset.
- [ ] A dump runs on a schedule, and you restored one to check it.
