Run the code on your machine, pass the checks CI runs, and open a pull request against `dev`.

## Prerequisites

- **Bun.** The repository pins `bun@1.3.14` in `package.json`, and CI installs the latest Bun.
- **Node.js 20.19+, 22.12+ or 24+.** `bun install` runs Prisma's install script, which refuses other Node versions.
- **Docker with Compose v2.**

Then clone the repository and install:

```bash
git clone https://github.com/suiramdev/freenary.git
cd freenary
bun install
```

## Run it in Docker

```bash
bun run dev:up
```

It starts PostgreSQL, applies the migrations, and runs the API server, the web app and the documentation site with live reload. It prints the addresses it serves:

- `http://web.<slug>.freenary.localhost`
- `http://server.<slug>.freenary.localhost`
- `http://docs.<slug>.freenary.localhost`

The slug comes from your git branch, so two worktrees run side by side. A shared Traefik container on port 80 routes these hostnames. Use Chrome or Firefox, which resolve `*.localhost` on their own.

`bun run dev:logs` follows the logs, `bun run dev:down` stops everything, and `bun run dev:reset` deletes the database and starts over.

There's no seed data. Create an account on the sign-in screen: with no email provider, sign-up signs you in at once.

To work on emailed codes, start with `bun run dev:mail` instead. It adds a Mailpit inbox at `http://mail.<slug>.freenary.localhost`, and the server sends every email there.

### Bank data without credentials

When `.env` sets none of `BANKING_PROVIDER`, `POWENS_CLIENT_ID` and `ENABLE_BANKING_APP_ID`, `bun run dev:up` starts the server with `BANKING_PROVIDER=mock`, and prints `bank    mock provider, generated data`. The environment then owns `BANKING_PROVIDER`, so the setup screen can't pick another bank provider, and one saved there before is ignored. To use a real provider, set one of the three in `.env`.

The mock provider lists three made-up banks for every country. Connecting one opens a consent page on the API server: **Approve** returns to Freenary with a new connection, and **Decline** returns to Freenary as a refused consent. Each connection gets a checking account and a Livret A, and some also get a PEA or a life-insurance contract.

The checking account books French bank descriptors: card payments, direct debits, rent, a monthly salary and cash withdrawals. A day's transactions stay the same from one sync to the next, so a sync only adds the days since the last one. Today's card payments arrive as pending. Holdings take a new price every day.

## Run it without Docker for the apps

Only PostgreSQL runs in Docker:

```bash
cp .env.example .env
echo 'DATABASE_URL=postgresql://postgres:password@localhost:5432/freenary' > apps/server/.env
docker compose up -d --wait postgres
(cd packages/db && bun run db:migrate:deploy)
bun run dev
```

The server listens on port 3000, the web app on 3001 and the documentation site on 4000.

To use the mock bank provider on this path, add `BANKING_PROVIDER=mock` to `apps/server/.env`.

## Checks

CI runs `bun install --frozen-lockfile`, then these steps in order. Run them before you push:

```bash
bun run check         # Lint & format
bun run check-types   # Type check
bun run check:fsd     # Architecture
bun run docs:check    # Documentation
bun run env:check     # Environment
(cd packages/api && bun test)   # API tests
bun run build         # Build
```

`bun run fix` repairs most lint and format errors. A second CI job parses every Compose file.

On each commit, lefthook runs three jobs on the staged files, one after another, and stops at the first that fails:

- `oxlint --fix`, then stages the fixes.
- `oxfmt --write`, then stages the fixes.
- `bun run env:sync`, when the commit touches `packages/env/src/schema*.ts`, a `docker-compose*.yml` file or `scripts/env-sync.ts`.

## Tests

CI runs the `packages/api` tests, the **API tests** step above, and no other test file. There's no root `test` script. Run the other files your change touches, in `apps/web`, the other packages and `scripts/`:

```bash
bun test scripts/dev-identity.test.ts
```

## Pull requests

Open your pull request against `dev`. `main` holds released code. [`CONTRIBUTING.md`](https://github.com/suiramdev/freenary/blob/dev/.github/CONTRIBUTING.md) has the rules: branch names, the pull request template, signed-off commits, documentation in the same change.

The template's Evidence section is optional. For a change people can see, drag screenshots or a screen recording into it so GitHub hosts them. Use fake data only: no real keys, tokens or personal data, and no file paths from your machine. Reviewers check it on an interface change and ask for it when it's missing; no check fails without it. Delete the section when it doesn't apply, and say "no visual change" in Notes.

Maintainers cut releases from `main` with the `Release` workflow. Don't tag, and don't bump a version.

## Find an issue

Issues labelled [`good first issue`](https://github.com/suiramdev/freenary/labels/good%20first%20issue) are small and fully specified. Issues labelled [`help wanted`](https://github.com/suiramdev/freenary/labels/help%20wanted) are fully specified and open to anyone. Comment on the issue to claim it, and wait for a maintainer to assign it to you. A claim with no pull request and no update for 14 days can be given to someone else. [`CONTRIBUTING.md`](https://github.com/suiramdev/freenary/blob/dev/.github/CONTRIBUTING.md#working-on-an-issue) has the details.

## Labels

Open an issue with the bug report, feature request, specified task or other form. Write the title plainly: the forms add no `[Bug]` or `[Feature]` prefix. Use the specified task form when you can state the context, the expected behavior, the acceptance criteria and the files to start from. When part of the spec is still open, list it under **Still to define** as a checklist. An issue with an open item never carries `good first issue` or `help wanted`.

The repository has twelve labels. A `type:` label is `type: bug`, `type: feature`, `type: documentation` or `type: maintenance`. An `impact:` label is `impact: high`, `impact: medium` or `impact: low`, and a `priority:` label is `priority: high`, `priority: medium` or `priority: low`. The last two are `good first issue` and `help wanted`. No label says where an item stands: that is whether it is assigned and linked to a pull request.

The `Triage` workflow labels an issue or pull request with SubQ Snap (`subq-snap-1.1`) when it is opened or reopened. It runs again when someone edits the title or description, when the author replies, and when someone adds a `type:`, `impact:` or `priority:` label, or `help wanted` or `good first issue`. On a pull request from a branch of this repository, it also runs when the `CI` workflow finishes. It skips closed items, skips a draft pull request until it is marked ready for review, and skips events a bot triggers. It labels nothing when the repository has no `SUBQ_API_KEY` secret. A maintainer reruns it from the Actions tab with an item number.

The workflow adds one `type:` label to an issue or a pull request, and applies the model's top answer whatever its confidence. An exact tie goes to the option listed first in `scripts/triage/questions.ts`. A group with no usable answer gets no label. The run's summary and its `triage-record.json` artifact list the answers with their confidence and, when the model returns probabilities, the runner-up. The model reads the title, the description and the author's replies.

On an issue, the workflow adds the model's most probable `impact:` label, whatever its confidence. An exact tie goes to the higher level. When the model returns no probability per level, the workflow rounds its impact score. `impact: high`, `impact: medium` and `impact: low` give `priority: high`, `priority: medium` and `priority: low`. A regression, found with at least 0.80 probability, raises that priority by one level. A security risk, found with the same probability, gives `priority: high`. Neither sets a priority without an impact. With no usable impact answer, neither label is applied. An `impact:` label already on the item replaces the model's impact. The workflow recomputes a `priority:` label it set itself on each run, and removes it when a maintainer adds another `priority:` label. A pull request gets a `type:` label and nothing else. When the model's most probable answer names another open item as the same request, with at least 0.85 probability, the workflow asks a maintainer to check for a duplicate, and adds no label.

The workflow adds `good first issue` when the model's most probable answer, whatever its confidence, is that a newcomer could finish the work. An exact tie adds nothing. The spec must also be complete: nothing missing from the checklist below, nothing open under **Still to define**, and the issue not blocked. It removes a `good first issue` label it added when that stops being true, but not when a later answer changes. While an item is open under **Still to define**, it removes `good first issue` and `help wanted` whoever added them, and lists the open items for a maintainer. It never adds `help wanted`: a maintainer adds it once the spec is complete.

The checklist for an issue depends on its type:

- A bug needs the steps that show it, what happened and what you expected, and the version or deployment.
- A feature needs the problem, the expected result, and no open design choice.
- A documentation issue needs the page and what is wrong on it.
- A maintenance issue needs what should change and why, and no open design choice.
- A pull request needs a written Summary, every section of the template filled except the optional Evidence, and passing `ci` and `compose` checks. When it changes documented behaviour and no page under `content/docs/next`, its Notes must name the pages or say why none needed a change.

When something is missing, the workflow posts one comment that lists it, for the author and for a maintainer. It updates that comment when the list changes. It deletes the comment once nothing is missing, when the item is blocked, when only a running check is left, or when a maintainer has set a `priority:` label. An open **Still to define** item keeps the comment. The workflow never replaces a group a maintainer already labelled, and never adds back a label that someone else removed.

`scripts/triage/taxonomy.ts` defines every label. The `Labels` workflow creates and updates them when that file changes on `dev` or `main`, and never deletes one. [`docs/engineering/triage.md`](https://github.com/suiramdev/freenary/blob/dev/docs/engineering/triage.md) describes the whole process.
