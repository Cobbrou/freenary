Look up any variable here: its default, what it does, and what happens when it's missing or wrong. Bank and email credentials normally go in the setup screen, not in a file.

## Where a value goes

| You run | Put variables in | Required |
| --- | --- | --- |
| `deploy/docker-compose.yml` (Dokploy, Portainer, a proxy on a Docker network) | The panel's environment, or a `.env` next to the file | `FREENARY_URL`, `POSTGRES_PASSWORD`, `BETTER_AUTH_SECRET` |
| `deploy/coolify.yml` | The `server` service's `environment:` list, then the resource's **Environment Variables** tab ([below](#add-a-variable-on-coolify)) | Nothing. Coolify generates the secrets and the URL |
| `docker-compose.yml` at the repository root (ports published on the host) | `.env` next to the file | `POSTGRES_PASSWORD`, `BETTER_AUTH_SECRET`, and in practice `BETTER_AUTH_URL` and `CORS_ORIGIN` |
| Bank and email credentials, on any of the above | [The setup screen](#setup-screen-or-environment) at `/setup` | — |

**`deploy/docker-compose.yml`.** `FREENARY_URL` is the one public URL of the instance, for example `https://freenary.example.com`. It fills `BETTER_AUTH_URL`, `CORS_ORIGIN` and `PUBLIC_SERVER_URL`, so the browser, the web app and the API server all use one address. The value must match the browser address bar exactly, scheme included, or every sign-in fails.

**`deploy/coolify.yml`.** Coolify fills those same three variables from the domain you give the `web` service, and generates the database password and `BETTER_AUTH_SECRET`.

**Root `docker-compose.yml`.** Compose reads the `.env` next to the file. The `server` service loads every line of it, but five keys in the compose file win over `.env`:

| Key on `server` | Value |
| --- | --- |
| `DATABASE_URL` | Built from `POSTGRES_PASSWORD`. A `DATABASE_URL` line of your own does nothing |
| `BETTER_AUTH_SECRET` | Your `.env` value |
| `BETTER_AUTH_URL` | Your `.env` value, default `http://localhost:3000` |
| `CORS_ORIGIN` | Your `.env` value, default `http://localhost:3001` |
| `NODE_ENV` | Always `production` |

For one hostname, set `BETTER_AUTH_URL` and `CORS_ORIGIN` to the same URL. See [Reverse proxy](/docs/reference/reverse-proxy).

<Callout type="warn">

The `web` service reads no `.env` line. It gets `SERVER_URL` (`http://server:3000`) and `PUBLIC_SERVER_URL`, which Compose copies from `BETTER_AUTH_URL`. To change the address the browser calls, change `BETTER_AUTH_URL`.

</Callout>

`migrate` gets `DATABASE_URL` alone. `postgres` gets `POSTGRES_DB`, `POSTGRES_USER` and `POSTGRES_PASSWORD`, and the first two are fixed in the compose file.

After editing `.env`, apply it with `docker compose up -d`. Compose recreates the changed containers; no image rebuild is needed.

### Add a variable on Coolify

Coolify passes a container only the variables its compose file names. `deploy/coolify.yml` names none of the optional ones, so a variable you only add under **Environment Variables**, such as `AI_BASE_URL` or `OIDC_DISCOVERY_URL`, never reaches the server. Open **Edit Compose File** and add one line per variable to the `environment:` list of the `server` service:

```yaml
- AI_BASE_URL=${AI_BASE_URL}
- AI_MODEL=${AI_MODEL}
```

Save. Coolify then lists each one under **Environment Variables**: fill in the values and redeploy.

## Setup screen or environment

The setup screen (`/setup`) is where the operator enters bank and email credentials. It owns these variables:

| Integration | Variables |
| --- | --- |
| Bank provider | `BANKING_PROVIDER`, `POWENS_DOMAIN`, `POWENS_CLIENT_ID`, `POWENS_CLIENT_SECRET`, `ENABLE_BANKING_APP_ID`, `ENABLE_BANKING_PRIVATE_KEY` |
| Email delivery | `EMAIL_PROVIDER`, `EMAIL_FROM`, `RESEND_API_KEY`, `SMTP_HOST`, `SMTP_PORT`, `SMTP_SECURE`, `SMTP_USER`, `SMTP_PASSWORD` |

Every other variable comes from the environment alone. A few must stay there, because Freenary needs them before it can serve the screen: `POSTGRES_PASSWORD`, `BETTER_AUTH_SECRET`, the public URL (`FREENARY_URL`, or `BETTER_AUTH_URL` and `CORS_ORIGIN`) and `FREENARY_VERSION`.

### A value in the environment wins

The server reads each variable from the environment first, and falls back to what the setup screen saved. An empty value counts as unset.

- A variable set in the environment shows on the screen as read-only, tagged `Set by your server`.
- The screen shows the first four and last four characters of such a value, or `…` for a value of eight characters or fewer. It never shows a secret. `SMTP_PORT` and `SMTP_SECURE` show in full.
- `Save and continue` tests the environment values together with what you typed, and stores only the fields the environment doesn't set.
- When the environment alone configures a provider completely, the step shows a ready card with a `Test connection` button instead of the form.

This lets you keep secrets in a `.env`, Kubernetes or Vault; the screen never fights it. To hand a value to the screen instead, delete its line from the environment and run `docker compose up -d`.

<Callout type="warn">

Saving one bank provider on the setup screen clears the stored credentials of the other one. Connections made with the old provider then can't sync or disconnect. To switch providers and keep old connections working, put the old provider's credentials in the environment first.

</Callout>

### Where setup values are stored

Each value is one row of the `instance_setting` table, sealed with AES-256-GCM under a key derived from `BETTER_AUTH_SECRET`. The row name is bound to the sealed value, so a row copied to another name won't open. The screen never sends a stored secret back to the browser; an empty secret field keeps the current value.

What follows from that:

- A database dump contains the credentials. Protect it like the `.env` file.
- A new `BETTER_AUTH_SECRET` makes every stored value unreadable. The server logs one warning per row and turns that integration off until the operator enters it again.
- The server reads the stored values once, at startup. `Finish setup` restarts the server when a saved value isn't in use yet. That relies on the container restart policy: both Compose files set `restart: unless-stopped`, and `deploy/coolify.yml` relies on Coolify's own. If the server doesn't come back, see [Troubleshooting](/docs/run/troubleshooting#the-server-does-not-restart-after-setup).
- If the stored values fail validation at startup, the server ignores all of them, runs on the environment alone, and the setup screen shows `Configuration problem` with the reason.

## Startup checks

{/* env-sync:start count */}

The API server checks its environment once, at startup. The schema is [`packages/env/src/schema.ts`](https://github.com/suiramdev/freenary/blob/main/packages/env/src/schema.ts). It declares 48 variables with Zod, and `packages/env/src/server.ts` hands them to `@t3-oss/env-core`. The reference below, and `.env.example`, are generated from that one file.

{/* env-sync:end */}

- An empty string counts as unset. `PORT=` is the same as no `PORT`, so the default applies.
- A bad value stops the process before it opens a port, and the server prints the variable that failed:

```bash
❌ Invalid environment variables: [
  {
    origin: "string",
    code: "invalid_format",
    format: "regex",
    pattern: "/^\\d+$/u",
    path: [ "PORT" ],
    message: "PORT must be a decimal number between 1 and 65535",
  }
]
error: Invalid environment variables
```

<Callout type="error">

Never set `SKIP_ENV_VALIDATION` at runtime. It turns the whole schema off, so the server starts with a broken configuration. `apps/server/Dockerfile` sets it in the `builder` stage only, because a build has no database and no secret.

</Callout>

### What stops a start

| Mistake | Who refuses | Message |
| --- | --- | --- |
| `POSTGRES_PASSWORD` or `BETTER_AUTH_SECRET` unset or empty | Compose, before any container | `Set POSTGRES_PASSWORD in .env`, `Set BETTER_AUTH_SECRET in .env` (`deploy/docker-compose.yml` words them slightly differently) |
| `FREENARY_URL` unset or empty | `deploy/docker-compose.yml` | `Set FREENARY_URL to the public URL of the web app, such as https://freenary.example.com` |
| No `.env` next to the root `docker-compose.yml` | Compose, on the `env_file` of `server` | Compose names the missing file |
| `FREENARY_VERSION` names a tag that doesn't exist | The image pull | `not found` |
| `BETTER_AUTH_SECRET` under 32 characters | The schema | The invalid-environment report, then exit |
| A value outside its enum, URL format or number range | The schema | The invalid-environment report, then exit |
| `NODE_ENV=production` with no `BETTER_AUTH_SECRET`, `DATABASE_URL`, `BETTER_AUTH_URL` or `CORS_ORIGIN` | The schema | The invalid-environment report. Those defaults apply outside production only |
| `TRUSTED_PROXIES` with an IPv4-mapped entry | The schema | `write an IPv4-mapped address in its IPv4 form, e.g. 10.0.0.0/24` |
| `EMAIL_PROVIDER=resend` with no key | The email registry | `EMAIL_PROVIDER=resend requires RESEND_API_KEY to be set.` |
| `EMAIL_PROVIDER=smtp` with no sender | The email registry | `EMAIL_PROVIDER=smtp requires EMAIL_FROM to be set.` |
| `AUTH_COOKIE_DOMAIN` with a trailing dot, a single label, or not a parent of both hostnames | The cookie policy | A message that names the value and the fix |
| Two hostnames, no `AUTH_COOKIE_DOMAIN`, and `BETTER_AUTH_URL` on plain HTTP | The cookie policy | `The API (<api origin>) and the web app (<web origin>) are on different hosts, so the session cookie needs SameSite=None — which browsers reject over plain HTTP. …` |
| The `instance_setting` table can't be read, for example the database is unreachable | The setup values loader, in production | The error, then exit |

Outside production, the two-hostname cookie check is only a warning. The self-hosting Compose files set `production`, so a deployed instance always gets the refusal. `EMAIL_PROVIDER=resend` checks the key before the sender, and `smtp` checks the sender before the host, so a setup missing both reports the first.

## Core and secrets

{/* env-sync:start core */}

| Variable | Default | What it does | Absent or wrong |
| --- | --- | --- | --- |
| `BETTER_AUTH_SECRET` | `dev_secret_change_me_at_least_32chars` outside production, required in production | Signs session cookies, encrypts two-factor secrets and backup codes, and signs the bank connection state. | Under 32 characters stops the start. The development default applies outside production alone, so a production start with no value stops. |
| `NODE_ENV` | `development` | Picks the runtime mode: `development`, `production` or `test`. | `production` drops the log file drain and turns the cookie warning into a refusal. `test` turns the sign-in rate limits off. Compose always sets `production`. |
| `PORT` | `3000` | The port the API server listens on. It also fills the `BETTER_AUTH_URL` default. | A non-digit character stops the start. In the Docker stack it must stay `3000`, because the healthcheck fetches port 3000 inside the container. Never put it in the root `.env` file, which the `server` service loads whole. |

{/* env-sync:end */}

To change the host port, use `SERVER_PORT`, never `PORT`.

A new `BETTER_AUTH_SECRET` signs everyone out, resets every two-factor enrolment and makes the setup values unreadable. See [Security](/docs/reference/security).

## Public URLs and cookies

{/* env-sync:start origins */}

| Variable | Default | What it does | Absent or wrong |
| --- | --- | --- | --- |
| `AUTH_COOKIE_DOMAIN` | unset | The parent domain the API server and the web app share, for example `.example.com`. It keeps the session cookie at `SameSite=Lax` and adds `Domain`. | Three shapes stop the start: a trailing dot, a single label, and a domain that is not a parent of both hostnames. Unset with two hostnames drops the cookie to `SameSite=None`. |
| `BETTER_AUTH_URL` | `http://localhost:3000` outside production, required in production | The public origin of the API server. It builds the sign-in callback URLs and decides the cookie `Secure` flag. | A value that is not a URL stops the start. A wrong origin breaks every sign-in callback. |
| `CORS_ORIGIN` | `http://localhost:3001` outside production, required in production | The public origin of the web app. It sets the CORS allow-list, the passkey relying party and the cookie same-site test. | A wrong value makes the browser report a CORS failure, and it binds passkeys to the wrong relying party. |
| `TRUSTED_PROXIES` | unset | The addresses or CIDR ranges of the proxies in front of the API server. Rate limits key on the caller address behind them. | A malformed entry stops the start. Unset behind a multi-hop proxy makes every caller share one rate-limit bucket. |

{/* env-sync:end */}

With one hostname, `AUTH_COOKIE_DOMAIN` stays unset. See [Reverse proxy](/docs/reference/reverse-proxy) for two subdomains and trusted proxies.

| --- | --- | --- | --- |

## Assistant

{/* env-sync:start assistant */}

| Variable | Default | What it does | Absent or wrong |
| --- | --- | --- | --- |
| `AI_API_KEY` | unset | The key for that endpoint. | Unset is valid, because a local endpoint needs no key. |
| `AI_BASE_URL` | unset | The base URL of the chat-completions endpoint, with its version path. | A value that is not a URL stops the start. Unset means the instance reports no server model. |
| `AI_MODEL` | unset | The model id as the endpoint names it. | It needs `AI_BASE_URL` too. With either one unset, the assistant route answers `503 unconfigured`. |

{/* env-sync:end */}

Any OpenAI-compatible chat-completions endpoint works. Freenary posts to `<AI_BASE_URL>/chat/completions`, and the model must support tool calling, or it invents figures without reporting an error.

```dotenv
# A hosted gateway
AI_BASE_URL=https://openrouter.ai/api/v1
AI_API_KEY=<your key>
AI_MODEL=<model id>
```

```dotenv
# A runtime on your own server, as a service on the same Docker network
AI_BASE_URL=http://ollama:11434/v1
AI_MODEL=<model id>
```

`http://localhost:11434/v1` would point at the API server container itself. See [Assistant](/docs/use/assistant) for what each question sends.

## Categorisation

{/* env-sync:start categorisation */}

| Variable | Default | What it does | Absent or wrong |
| --- | --- | --- | --- |
| `DICTIONARY_PUBLIC_KEY` | unset | An Ed25519 public key in PEM form. A value turns signature checks of the merchant dictionary on. | Unset loads the dictionary with no check. A set key with no signature file makes the loader refuse the dictionary, and it warns `Dictionary signature missing:`. |
| `TRANSACTION_CLASSIFIER` | unset | Names the protocol of the classifier asked first for a merchant no rule, no dictionary entry and no correction knows. `system-one` posts the TypeSafe `/v1/systemone` shape, which TypeSafe Jev, `Mapika/decider-2b` and Laya all answer. `llm` posts an OpenAI-compatible chat completion. `zero-shot` posts the Hugging Face zero-shot-classification shape. | Unset calls no model, and such a transaction stays uncategorised. Any other value stops the start. |
| `TRANSACTION_CLASSIFIER_API_KEY` | unset | The key that endpoint expects, if it expects one. | Unset sends no authorisation header at all, which a local endpoint accepts. |
| `TRANSACTION_CLASSIFIER_ESCALATE_BELOW` | `0.85` | The confidence under which the answer of the first classifier goes to `TRANSACTION_CLASSIFIER_FALLBACK`. The default is the confidence the pipeline needs to write a category without asking the reader. | A value outside 0 to 1 stops the start. At 0 the fallback answers abstentions alone. |
| `TRANSACTION_CLASSIFIER_FALLBACK` | unset | Names the protocol of the classifier asked when the first one abstains or answers under `TRANSACTION_CLASSIFIER_ESCALATE_BELOW`. The higher-confidence answer of the two wins, and each is cached against its own model. | It needs `TRANSACTION_CLASSIFIER` too. The same protocol and the same model as the first slot stops the start, because both would share one cache row. |
| `TRANSACTION_CLASSIFIER_FALLBACK_API_KEY` | unset | The key the fallback endpoint expects, if it expects one. | Unset sends no authorisation header at all. |
| `TRANSACTION_CLASSIFIER_FALLBACK_MODEL` | unset | Names the model the fallback endpoint serves. It is part of the cache key, so a change asks every merchant again. | A named fallback with no model stops the start with `TRANSACTION_CLASSIFIER_FALLBACK=<protocol> requires TRANSACTION_CLASSIFIER_FALLBACK_MODEL to be set.` |
| `TRANSACTION_CLASSIFIER_FALLBACK_TEMPERATURE` | `1` | Sharpens or flattens the answer distribution of the fallback before its confidence is measured. It follows the same rule as `TRANSACTION_CLASSIFIER_TEMPERATURE`. | A value that is not a positive number stops the start. A value above 1 lowers the confidence of an over-confident model. |
| `TRANSACTION_CLASSIFIER_FALLBACK_URL` | unset | The URL of the fallback endpoint. The `llm` protocol appends `/chat/completions` to it, and the other two post to it as it is. | A value that is not a URL stops the start. A named fallback with no URL stops it too. |
| `TRANSACTION_CLASSIFIER_MODEL` | unset | Names the model that endpoint serves. It is part of the cache key, so a change asks every merchant again. | A named classifier with no model stops the start with `TRANSACTION_CLASSIFIER=<protocol> requires TRANSACTION_CLASSIFIER_MODEL to be set.` |
| `TRANSACTION_CLASSIFIER_TEMPERATURE` | `1` | Sharpens or flattens the answer distribution before the confidence is measured. At 1 a `system-one` endpoint keeps the statistic it reports, and the other two protocols still measure the distribution themselves. | A value that is not a positive number stops the start. Fit it on merchants your own readers corrected. |
| `TRANSACTION_CLASSIFIER_URL` | unset | The URL of the endpoint the classifier asks. The `llm` protocol appends `/chat/completions` to it, and the other two post to it as it is. It reaches a server you run or one somebody else hosts. | A value that is not a URL stops the start. An `llm` endpoint that returns no `logprobs` leaves every answer a suggestion. |

{/* env-sync:end */}

A classifier request carries `normalisedDescriptor`, `merchantKey`, `counterpartyName`, `merchantCategoryCode`, `direction`, `amountBucket`, `currency`, `country`, `channel` and `path`. It carries no exact amount, date, IBAN, account or user. For a transfer or direct debit, `merchantKey` is left out, because there it is the creditor account number. Answers are cached per merchant across the whole instance, so each merchant is asked about once.

<Callout type="warn">

Leave `DICTIONARY_PUBLIC_KEY` unset. The published merchant dictionary carries no signature, so a set key makes the server refuse it, log `[categorisation] Dictionary signature missing: <path> — refusing to load`, and stop matching merchants. The schema doesn't check the key's format, so nothing catches this at startup. Set it only when you sign a dictionary yourself (`cd packages/api && bun run generate:key`).

</Callout>

## Not in the schema

The code reads these straight from `process.env`, so a typo produces no startup error.

{/* env-sync:start raw */}

| Variable | Read by | What it does |
| --- | --- | --- |
| `DEV_PUBLIC_URL` | the web and documentation dev servers | The address the web and documentation dev servers print in place of their container address. Compose sets it from `WEB_HOST` and `DOCS_HOST`. |
| `PUBLIC_SERVER_URL` | the web app, per request | The API origin the web app hands to the browser in the root document. Compose sets it from `BETTER_AUTH_URL`. A value that is not an absolute URL throws `PUBLIC_SERVER_URL must be an absolute URL such as https://api.example.com, got "…"`. |
| `SERVER_URL` | the web app, on the server side | The origin the web app itself calls while it renders a page. It wins over `PUBLIC_SERVER_URL` there. The web app also forwards the API paths it receives (`/api/auth`, `/rpc`, `/ai/chat` and `/api-reference`) to it, so one public origin can serve both apps. Compose sets `http://server:3000`. |
| `SKIP_ENV_VALIDATION` | the API server | Any non-empty value turns the whole server schema off. The image sets it in the builder stage alone. |
| `GITHUB_REPOSITORY` | the server image build | Which repository the merchant data release comes from. The default is `suiramdev/freenary`. |
| `GITHUB_TOKEN` | the server image build | It lifts the GitHub API rate limit of that download. The build reads it as a BuildKit secret, so the value never enters a layer. |
| `OPENROUTER_API_KEY` | the documentation site | The OpenRouter key behind the `Ask AI` panel of the documentation site. That app carries no workspace dependency, so it declares no schema. |
| `OPENROUTER_MODEL` | the documentation site | The model that panel asks. The site carries its own default, so the value is optional. |

{/* env-sync:end */}

`VERCEL_ENV`, `VERCEL_URL` and `VERCEL_PROJECT_PRODUCTION_URL` are read by the web app only when `VITE_SERVER_URL` is a relative path, which never happens in Docker.

These two belong to the web app's client schema. Vite builds them into the bundle, so the image build decides their values:

{/* env-sync:start client */}

| Variable | Default | What it does |
| --- | --- | --- |
| `VITE_FREENARY_VERSION` | none | The release the account menu links to. `1.2.0` opens the `1.2` documentation; any other value, and an empty one, opens the `next` documentation. The Dockerfile fills it from the `FREENARY_VERSION` build argument. |
| `VITE_SERVER_URL` | `http://localhost:3000` | The build-time fallback API origin. It applies only while `SERVER_URL` and `PUBLIC_SERVER_URL` are both unset. |

## Compose-only variables

No application code reads these; they configure the containers.

{/* env-sync:start compose */}

| Variable | Default | What it does | Absent or wrong |
| --- | --- | --- | --- |
| `POSTGRES_PASSWORD` | none | The database password. It fills both the container password and the `DATABASE_URL` of `migrate` and `server`. | Compose refuses an unset or empty value. |
| `FREENARY_VERSION` | `latest` | The tag of both published images. | An unset value falls back to `latest`, the newest release. A value that names no tag fails the pull with `not found`. The tags are `X.Y.Z`, `X.Y`, `X`, `latest`, `main`, `dev` and `sha-<7 characters>`. |
| `FREENARY_URL` | none | The public URL of the web app in `deploy/docker-compose.yml`, the stack for a hosting panel. It fills `BETTER_AUTH_URL`, `CORS_ORIGIN` and `PUBLIC_SERVER_URL`, so the API server shares the web app origin. | `deploy/docker-compose.yml` refuses an unset or empty value. A value that differs from the browser origin makes every sign-in fail. |
| `SERVER_PORT` | `3000` | The host port of the API server. | — |
| `WEB_PORT` | `3001` | The host port of the web app. | — |
| `POSTGRES_PORT` | `5432` | The host port of PostgreSQL. Compose publishes `127.0.0.1:<POSTGRES_PORT>:5432`, so the loopback interface alone gets it. | — |

{/* env-sync:end */}

The development stack reads a few more. The production files ignore them, and [the local stack guide](https://github.com/suiramdev/freenary/blob/main/docs/engineering/local-stack.md) covers them:

{/* env-sync:start compose-dev */}

| Variable | Default | What it does |
| --- | --- | --- |
| `FREENARY_SLUG` | the git branch, else the directory name, else `dev` | Names the Compose project and every hostname of one worktree stack. It reaches Compose through the `-p` flag. |
| `SERVER_HOST` | `server.<slug>.freenary.localhost` | The API server hostname. It fills `BETTER_AUTH_URL`. |
| `WEB_HOST` | `web.<slug>.freenary.localhost` | The web app hostname. It fills `CORS_ORIGIN`. |
| `DOCS_HOST` | `docs.<slug>.freenary.localhost` | The documentation hostname, in the Traefik route alone. |
| `MAIL_HOST` | `mail.<slug>.freenary.localhost` | The Mailpit inbox hostname, in the Traefik route alone. It applies to `bun run dev:mail`. |
| `DOCS_PORT` | `4000` | The documentation port inside its own container. |

{/* env-sync:end */}

These appear in templates but do nothing in production:

{/* env-sync:start inert */}

| Variable | Why it does nothing |
| --- | --- |
| `POSTGRES_DB` | The production compose file hard-codes the database name `freenary`. The development stack does read the variable. |
| `POSTGRES_USER` | The production compose file hard-codes the user `postgres`. The development stack does read the variable. |

{/* env-sync:end */}

## Minimal files

`deploy/docker-compose.yml`, in the panel's environment or a `.env` next to it:

```dotenv
FREENARY_URL=https://freenary.example.com
FREENARY_VERSION=latest
POSTGRES_PASSWORD=<output of: openssl rand -hex 16>
BETTER_AUTH_SECRET=<output of: openssl rand -hex 32>
```

Root `docker-compose.yml`, behind your own proxy on one hostname:

```dotenv
FREENARY_VERSION=latest
POSTGRES_PASSWORD=<output of: openssl rand -hex 16>
BETTER_AUTH_SECRET=<output of: openssl rand -hex 32>
BETTER_AUTH_URL=https://freenary.example.com
CORS_ORIGIN=https://freenary.example.com
SERVER_PORT=127.0.0.1:3000
WEB_PORT=127.0.0.1:3001
```

Add bank and email credentials on the setup screen after the first sign-in.
