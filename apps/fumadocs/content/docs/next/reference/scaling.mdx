Use these limits to size one instance or add web and API replicas. PostgreSQL is the only durable runtime dependency and the first resource to watch.

## Shared state

The web service is stateless. API replicas share users, sessions, passkey challenges, rate-limit counters, bank data, assistant conversations and setup state through PostgreSQL. Sticky sessions aren't required.

Instance settings are read once when each API process starts. Restart every replica after changing the environment or setup-screen values. `Finish setup` exits only the API process that handled the request.

Production writes no application data to container disks. It schedules no background jobs, sync timers or cleanup timers. The only timer waits 250 milliseconds before that setup exit; a supervisor must start the process again.

Outside production, the event logger writes local files. Container engines and hosting panels also keep their own logs, so configure log rotation separately.

## One sync per user

A sync runs inside the API request that started it. Freenary claims one `sync_run` row for the user, so another tab or replica reads progress instead of starting duplicate work.

A process refreshes progress at most once a second. Another request can take over after five minutes without a write. The claim's start time prevents a displaced process from overwriting the new run's progress.

Users can sync concurrently with each other. Within one user's sync, bank connections, accounts and transaction writes run in sequence. Freenary has no worker queue or scheduled import.

## Connections per replica

Each API process creates two Prisma clients: one for the application and one for Better Auth. Each uses `PrismaPg` without a configured pool size, so the `pg` default applies.

The default is up to 10 connections per pool, or 20 per API replica. Leave room for migrations, backups and administration when setting PostgreSQL's connection limit or choosing a replica count.

Web replicas don't open database connections. The one-shot migration service opens its own client while a deployment starts.

## What grows

PostgreSQL grows with accounts, transactions, holdings, users, sessions and rate-limit keys. It also retains assistant conversations after a user starts a new one, and caches classifier results by input signature.

A forced sync upserts the same provider transactions instead of appending another copy. Removing a bank connection cascades through its accounts, transactions and holdings.

The merchant dictionary lives inside the server image. It consumes image and per-process memory, not database or volume space.

## Volumes

Each production compose file has one PostgreSQL volume and no application volume:

| Compose file                | Logical volume           |
| --------------------------- | ------------------------ |
| `docker-compose.yml`        | `freenary_postgres_data` |
| `deploy/docker-compose.yml` | `freenary_postgres_data` |
| `deploy/coolify.yml`        | `freenary-postgres-data` |
| `docker-compose.dev.yml`    | `pgdata`                 |

Docker or the hosting panel prefixes the actual volume name with its project name. Back up the volume mounted at `/var/lib/postgresql`, not a guessed host name.

Scale only after monitoring database connections, query latency, sync duration, memory and disk growth. [API](/docs/reference/api) describes the request limits; [Updates and backups](/docs/run/updates-and-backups) protects the shared state.
