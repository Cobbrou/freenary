One instance goes a long way: all state is in PostgreSQL, and the API server keeps nothing on disk. This page is for planning a bigger instance or a second API replica.

## What holds state

| Container | State |
| --- | --- |
| `postgres` | Everything, in one named volume mounted at `/var/lib/postgresql` |
| `server` | Nothing on disk. In memory: the merchant dictionary, loaded from the image, and the setup values, read once at startup |
| `web` | Nothing |
| `migrate` | Nothing. It applies migrations and exits |

The volume key is `freenary_postgres_data` in both Compose files. The root file sets the project name `freenary`, so Docker names the volume `freenary_freenary_postgres_data`. Coolify uses `freenary-postgres-data` with its own prefix. This is the one volume to size and back up.

## A second API replica

Nothing in the code prevents one. No Compose file sets up replicas or a load balancer, so the setup is yours. What they share:

- **Sessions** are read from the `session` table on every request. There's no cookie cache and no external store.
- **Rate limits** are counted in the `rate_limit` table, so replicas count into the same rows.
- **No background jobs.** There's no queue, scheduler, cron or Redis. A bank sync runs inside the request that started it, so two replicas can't run the same job twice.
- **No local files.** In production the server writes nothing to disk.

Each replica loads its own copy of the merchant dictionary from the same image, so they can't disagree.

<Callout type="warn">

Each replica reads the setup values once, at startup. `Finish setup` restarts only the replica that answered it. Restart every other replica afterwards, or they keep the old values. If the setup screen shows `The server did not restart`, restart all replicas and press `Try again`.

</Callout>

## Database connections

Each API replica opens two connection pools (two Prisma clients), each at the `pg` library's default size. PostgreSQL runs with the default `max_connections` of the `postgres:18` image. Each pool holds up to 10 connections, so plan on about 20 per replica against PostgreSQL's default limit of 100. No variable or URL parameter changes the pool size. Watch the connection count as you add replicas.

## Limits in the Compose files

| Setting | Value |
| --- | --- |
| CPU and memory limits | None |
| Log rotation | None: Docker's default driver, unbounded |
| Restart policy | `unless-stopped` on `postgres`, `server` and `web` in both Compose files. `deploy/coolify.yml` sets none and relies on Coolify |
| Health checks | `postgres`, `server` and `web`: every 10 s, 5 s timeout, 5 retries, plus a 10 s start period for the apps |
| Signals | `init: true` on `server` and `web` |

To cap a service, add limits in your copy of the Compose file:

```yaml
services:
  server:
    deploy:
      resources:
        limits:
          cpus: "1.0"
          memory: 1g
```

## What grows

- **The database volume**, with every account's transaction history. It only grows.
- **Calls to the model endpoint**, one or more per assistant question, capped at 30 questions per 300 seconds per user.

The merchant dictionary isn't state: each image update replaces it.

## What to measure

There's no metrics endpoint. Three numbers cover most needs:

| Number                 | Where                                             |
| ---------------------- | ------------------------------------------------- |
| PostgreSQL connections | `pg_stat_activity`                                |
| Volume size            | `docker system df -v`                             |
| API response codes     | The `server` container logs, one line per request |
