At the end of this page you run Freenary on your own machine, and you are signed in.

You need Docker Engine with Compose v2, and an account with a bank provider.

A bank connection is the only way transactions enter Freenary. No screen accepts a transaction by hand, so the install sets the provider up before the first start.

<Steps>

<Step>

### Get the two files

The stack runs published images, so it needs no source code. Two files are enough.

```bash
mkdir freenary && cd freenary
curl -O https://raw.githubusercontent.com/suiramdev/freenary/v0.1.0/docker-compose.yml
curl -O https://raw.githubusercontent.com/suiramdev/freenary/v0.1.0/.env.example
```

Every command below runs in that directory.

</Step>

<Step>

### Write the three values

Copy the template, then make the two secrets:

```bash
cp .env.example .env
openssl rand -hex 16   # POSTGRES_PASSWORD
openssl rand -hex 32   # BETTER_AUTH_SECRET
```

Open `.env` and write these three lines:

```dotenv
POSTGRES_PASSWORD=<the first value>
BETTER_AUTH_SECRET=<the second value>
FREENARY_VERSION=0.1
```

`BETTER_AUTH_SECRET` needs 32 characters or more. Compose stops before it creates a container when either secret is empty. It prints `Set POSTGRES_PASSWORD in .env` or `Set BETTER_AUTH_SECRET in .env`.

`FREENARY_VERSION` names the tag of both images. Five kinds of tag exist in the registry:

| Tag                  | What it holds                         |
| -------------------- | ------------------------------------- |
| `X.Y.Z`              | one release. The tag never moves      |
| `X.Y`                | the newest patch of that release line |
| `latest`             | the newest release                    |
| `main` or `dev`      | that branch, at its last push         |
| `sha-<7 characters>` | one commit                            |

`latest` is the fallback of the Compose file, and it moves at each release. Name the tag you want in `.env`. Read [Updates](/docs/self-hosting/updates) for what publishes each tag.

</Step>

<Step>

### Set up the bank provider

Powens is the default provider and the one to pick. A sandbox domain in the [Powens console](https://console.powens.com) is self-service, and it holds 50 connections.

<Callout type="warn">

**Powens registers an HTTPS redirect URI alone. It refuses `http://localhost`.**

A link ends at `<CORS_ORIGIN>/callback/powens` in the browser, and Powens sends the browser only to an origin you registered. The `localhost` stack of this page therefore lists banks and cannot finish a link.

So give the web app an HTTPS origin before you link a bank. [The served install](/docs/self-hosting) holds the two public origins. [Behind a reverse proxy](/docs/self-hosting/reverse-proxy) holds the TLS in front of them.

</Callout>

The console work takes four steps, and [Bank providers](/docs/self-hosting/bank-providers) walks each one:

1. Sign up, then create the organization the console asks for.
2. Create a domain. Powens makes it a sandbox and appends `-sandbox.biapi.pro`.
3. Create a client application, and register `<CORS_ORIGIN>/callback/powens` as its redirect URI.
4. Activate the connectors of the banks you want. A domain with no active connector answers with an empty list.

Write the credentials into the same `.env` file:

```dotenv
BANKING_PROVIDER=powens
POWENS_DOMAIN=acme-sandbox
POWENS_CLIENT_ID=<client id>
POWENS_CLIENT_SECRET=<client secret>
```

A later change of these values needs `docker compose up -d`. Compose recreates the `server` container with the new environment, and no image rebuild happens.

</Step>

<Step>

### Start the stack

```bash
docker compose up -d
```

Four services start: `postgres`, `migrate`, `server` and `web`. The `migrate` service applies the database migrations, then exits. The API server starts only after `migrate` exits with `0`. `migrate` runs again on every later start, and it repeats no work. You never run a migration command yourself.

</Step>

<Step>

### Check the two services

```bash
curl http://localhost:3000/
curl -L -o /dev/null -w '%{http_code} %{url_effective}\n' http://localhost:3001/
```

The API server answers with the plain string `OK`. The web app sends a visitor with no session to the sign-in screen. The second command therefore prints `200 http://localhost:3001/login`.

Read [Troubleshooting](/docs/self-hosting/troubleshooting) when a command answers something else.

</Step>

<Step>

### Create the first account

Open `http://localhost:3001` in a browser. The screen reads `Welcome to Freenary`.

1. Type your email address. Freenary finds no account for it, and shows a `Name` field and a `Password` field.
2. Write a name of 2 characters or more, and a password of 12 characters or more.
3. Press `Create account`.

With no email provider configured, Freenary signs you in at once and opens the onboarding wizard. With one configured, the screen moves to `Confirm your email` and asks for the 6-digit code it sent you. That code lives 10 minutes. Freenary signs you in after you enter it.

Freenary has no admin account and no owner role. The first account is an ordinary user.

</Step>

</Steps>

## What you have now

- You are signed in to your own instance.
- Your account sits in the PostgreSQL database of that instance.
- **Settings** lists the banks of your tax residencies, because the credentials of the provider are set.
- No bank is connected, so the Budget screen asks you to connect one.

[Connect a bank](/docs/guides/bank-connections) covers the link itself.
