This page installs an instance that serves other people. It needs real secrets, two public origins and TLS in front.

[Quickstart](/docs/quickstart) owns the other job: one instance on `localhost`, for you alone. Start there when nobody else must reach it.

## Before you start

| Need | Detail |
| --- | --- |
| Docker | Docker Engine and Docker Compose v2 on the host. |
| Host | Any operating system that runs Docker. Both images exist for `linux/amd64` and `linux/arm64`. That pair is the container platform, not the host. |
| PostgreSQL | Version 18. The stack runs it as a service, so you install no database. |
| Public origins | One for the web app, and one for the API server. |
| TLS | A proxy in front of both origins. Read [Behind a reverse proxy](/docs/self-hosting/reverse-proxy). |

**A bank provider decides whether the instance is useful.** No screen takes a transaction by hand, so an instance with no provider serves empty screens. Set one up in the same sitting. [Bank providers](/docs/self-hosting/bank-providers) walks the Powens console, and a sandbox domain needs no contract.

An email provider and a model endpoint stay optional. Each one has its own page: [Email](/docs/self-hosting/email) and [Assistant](/docs/self-hosting/assistant).

## The four services

`docker-compose.yml` declares the Compose project `freenary`, four services and one named volume.

| Service | What it is | Published host port |
| --- | --- | --- |
| `postgres` | PostgreSQL 18, and the only service that holds state | `127.0.0.1:${POSTGRES_PORT:-5432}:5432` |
| `migrate` | One command that applies the database migrations, then exits | none |
| `server` | The API server | `${SERVER_PORT:-3000}:3000` |
| `web` | The web app the browser loads | `${WEB_PORT:-3001}:3001` |

- `postgres` binds the loopback interface alone, so no other machine reaches the database over the network.
- `migrate` publishes nothing. It runs `bun x prisma migrate deploy` on every `up` and exits `0` when the schema is current.
- `server` and `web` publish on every interface. Put the proxy in front of both.
- Only `server` reads the root `.env` file. Read [Configuration](/docs/self-hosting/configuration).

## What the stack needs before it serves anybody

Two values are guarded in the compose file. Compose stops before it creates any container when either one is empty, and it names the value:

| Value                | The message Compose prints       |
| -------------------- | -------------------------------- |
| `POSTGRES_PASSWORD`  | `Set POSTGRES_PASSWORD in .env`  |
| `BETTER_AUTH_SECRET` | `Set BETTER_AUTH_SECRET in .env` |

Two more values name the public origins. Both default to `localhost`, which serves the host machine and nothing else:

| Variable | What it must hold |
| --- | --- |
| `BETTER_AUTH_URL` | The public origin of the API server, for example `https://api.example.com` |
| `CORS_ORIGIN` | The public origin of the web app, for example `https://app.example.com` |

Compose gives the `web` service `PUBLIC_SERVER_URL` from `BETTER_AUTH_URL`, so the browser calls the same API origin. A `PUBLIC_SERVER_URL` line of your own does nothing.

`FREENARY_VERSION` names the tag of both images. The compose default is `latest`, the newest release, and it moves at each one. Name a version such as `0.1` to hold an instance on one release line.

[Configuration](/docs/self-hosting/configuration) holds every variable, its default and its refusal message.

## Install

<Steps>

<Step>

### Get the two files

The stack runs published images, so it needs no source code. Two files are enough:

```bash
mkdir freenary && cd freenary
curl -O https://raw.githubusercontent.com/suiramdev/freenary/v0.1.0/docker-compose.yml
curl -O https://raw.githubusercontent.com/suiramdev/freenary/v0.1.0/.env.example
```

A clone gives the same two files, plus the source for a [build from source](/docs/self-hosting/from-source). Every command below runs from the directory that holds the two files.

</Step>

<Step>

### Write the secrets and the origins

```bash
cp .env.example .env
openssl rand -hex 16   # POSTGRES_PASSWORD
openssl rand -hex 32   # BETTER_AUTH_SECRET, 32 characters or more
```

The template ships a development value for both secrets. Replace both. These five lines are the minimum for a served instance:

```dotenv
POSTGRES_PASSWORD=<database password>
BETTER_AUTH_SECRET=<64 hex characters>
FREENARY_VERSION=0.1
BETTER_AUTH_URL=https://api.example.com
CORS_ORIGIN=https://app.example.com
```

Put your own hostnames in the last two lines. The API server refuses a secret under 32 characters at startup.

</Step>

<Step>

### Set up the bank provider

Do this before the first start, so the instance serves working screens from the beginning.

Create a sandbox domain and a client application in the [Powens console](https://console.powens.com). Register this redirect URI on the client:

```text
https://app.example.com/callback/powens
```

The value is your `CORS_ORIGIN` and the path `/callback/powens`. Powens matches it exactly, and it accepts HTTPS alone.

Activate the connectors of the banks you want to offer. A domain with no active connector answers with an empty bank list.

Then add the credentials of the client to `.env`:

```dotenv
BANKING_PROVIDER=powens
POWENS_DOMAIN=acme-sandbox
POWENS_CLIENT_ID=<client id>
POWENS_CLIENT_SECRET=<client secret>
```

[Bank providers](/docs/self-hosting/bank-providers) holds each console step, the sandbox limits, and the Enable Banking alternative. An empty `POWENS_` variable turns bank linking off, and no message says so.

</Step>

<Step>

### Start the stack

```bash
docker compose up -d
```

Compose pulls both images and starts `postgres`. It then runs `migrate` against the healthy database. `server` starts after `migrate` exits `0`, and `web` starts after `server` reports healthy. A fresh database therefore holds the whole schema before the first request arrives.

</Step>

<Step>

### Check that both ports answer

Ask the API server for its root path:

```bash
curl https://api.example.com/
```

It answers with the plain string `OK`.

Now ask the web app for its root page:

```bash
curl -L -o /dev/null -w '%{http_code} %{url_effective}\n' https://app.example.com/
```

The web app sends a caller with no session to the sign-in screen. The command therefore prints `200 https://app.example.com/login`. Without `-L`, a healthy web app answers a redirect to `/login`.

Read the service state next:

```bash
docker compose ps -a
```

`postgres`, `server` and `web` must all show `healthy`. `migrate` shows `Exited (0)`. The `-a` flag matters, because plain `docker compose ps` hides a container that already exited.

When a service does not answer, read its own output:

```bash
docker compose logs -f server
```

[Logs](/docs/self-hosting/logs) explains the format and what each line holds. [Troubleshooting](/docs/self-hosting/troubleshooting) matches a symptom to a cause.

</Step>

<Step>

### Create the first account

Open the web app origin in a browser, then sign up with an email address and a password. Freenary has no admin account and no owner role, so the first account is an ordinary user. [First steps](/docs/guides/first-steps) covers what that user does next.

The wizard that opens proves the bank provider. It asks for a tax residency, then offers a bank step with the banks your domain activated. A missing bank step means Freenary read no credentials, and Settings then reads `Bank linking is unavailable`.

</Step>

</Steps>

<Callout type="warn">

The first sign-up is the moment to decide about email verification. With no email provider, Freenary asks for no confirmation and a new account gets a session at once. Set a provider first when you want confirmed addresses and password reset. Read [Email](/docs/self-hosting/email).

</Callout>
