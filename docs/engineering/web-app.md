# Web application

Durable facts that the code cannot carry in a name. Each bullet names the module it belongs to. Source: comments deleted when the `no-comments` rule was adopted.

## Budget and sankey

- `apps/web/src/pages/budget/model/recurring.ts` (module) — the server detects the patterns and measures the months; every figure the Recurring view adds on top of that (monthly equivalent, annual cost, next occurrences, forecast, insights) is derived in the browser, so one payload serves the whole view and the arithmetic is testable without a database.
- `apps/web/src/pages/budget/model/recurring.ts › RECURRENCE_KINDS` — `fixed` is a commitment: same company, regular cadence, an amount that holds. `behavioral` is a repeated purchase: the company recurs, the amount does not.
- `apps/web/src/pages/budget/model/recurring.ts › rollForwardToNextSlot` — the detector cannot tell "not posted yet" from "paid, sync lagging", so a `nextExpected` already behind `asOf` rolls forward to its next slot rather than posing as due now.
- `apps/web/src/pages/budget/model/recurring.ts › recurringSummary` — the cost totals count `fixed` items only: a "left after recurring" figure that subtracted repeated groceries would answer a question nobody asked. The counts cover both kinds, because both fall due.
- `apps/web/src/pages/budget/model/recurring.ts › spendDenominator` — a declared plan is what the reader chose to spend and wins over observed income, which is only the fallback measurement. A zero on either side is no denominator at all, not a denominator of zero.
- `apps/web/src/pages/budget/model/recurring.ts › recurringTrend` — the server sends the trailing 12 calendar months, oldest first and zero-filled. The final entry is the month in progress and is dropped, because comparing a part month against whole ones reports a collapse that never happened; and a month with nothing outgoing at all is a month before the history begins, since the series counts discretionary spend too, so averaging it in fabricates a rise.
- `apps/web/src/pages/budget/model/recurring-filters.ts › filterRecurringItems` — detection reads a whole year in one response, so every recurring filter runs in the browser: narrowing the list costs no request and contradicts no chart. The amount bounds read against the monthly equivalent, which is the figure the filter sits beside, not the amount charged.
- `apps/web/src/entities/category/model/category-selection.ts › toggleGroup` — a ticked group drops its own categories from the filter because the server unions them in anyway; keeping the chips would raise the filter badge without changing a single result. It matters more with three groups than with sixteen: one `Spending` chip now stands for sixteen categories, so the alternative is sixteen chips that say the same thing.
- `apps/web/src/pages/budget/model/transaction-filters.ts › parseAmountBound` — reads a bound in the reader's own notation: `1,234.56` under `en` and `1 234,56` under `fr` are the same number, and both are what the list renders and a reader copies out of it. The locale says which separator groups, whatever is left of a decimal comma becomes a dot, and where several dots survive the last one is the decimal point. Anything else reads as no bound rather than as an error the reader then has to clear.
- `apps/web/src/shared/lib/sankey/apportion.ts › apportion` — money is fungible, so no apportionment is more true than another; but linking every source to every target needs N×M ribbons for the same totals and reads as a wash, while filling each target in turn needs at most N+M−1. Sources are consumed in the order given, and when they run short the trailing targets get no ribbon — which is what an overspent period looks like.
- `apps/web/src/shared/lib/sankey/apportion.ts › canContribute` — the positive-only test is what rejects `NaN`: its comparisons are false in both directions, so a source that was retried rather than skipped would spin forever.
- `apps/web/src/shared/lib/sankey/apportion.ts › UNMEASURABLE_TARGET_VALUE` — a non-finite target counts as zero. Left as `Infinity` it would pair with an infinite source and emit a non-finite ribbon value, and the layout does arithmetic on that.
- `apps/web/src/shared/lib/sankey/layout.ts › stackLinkBands` — a link may only join _adjacent_ columns, and anything else is dropped silently. Non-positive links are skipped before a port is consumed on either node, because the budget preview feeds `0` for an amount still being typed and a band there would render an empty ribbon.
- `apps/web/src/shared/lib/sankey/layout.test.ts › THREE_COLUMN_X_BEFORE_GENERALIZATION` — the column geometry the three-column engine produced before it was generalized, which the cash-flow chart is built on: `usable = CHART_WIDTH(700) − PAD.left(12) − PAD.right(12) = 676`, `colW = 676 × 0.22 = 148.72`, `gapW = (676 − 3 × colW) / 2 = 114.92`, hence `x = 12, 275.64, 539.28`.
- `apps/web/src/shared/lib/sankey/side-label.ts › fitSideLabel` — the amount is never sliced: `€2,500.00` cut to `€2…` reads as a different and entirely plausible figure, so when both will not fit the label survives whole and the amount is dropped. The ribbon's thickness already carries magnitude. `side-label.test.ts › amountWholeOrAbsent` states that as "carries the amount in full or carries no digits at all", because `formatCurrency` may lead or trail the symbol by locale and a symbol-shaped regex would miss a digit-side cut.
- `apps/web/src/pages/settings/model/budget-profile-sankey.ts › toBudgetProfileSankey` — grouping by category _group_ rather than by category is what makes this chart read the same as the cash-flow one. Its middle column is the three flow sections, so the diagram reads as the revenue, savings and spending split rather than as a list of topics. Investments are ordered ahead of outgoings so the allocation side follows the order the profile is entered, and each group's lines are emitted immediately after their group so the ribbons do not cross.

## Browser assistant

- `apps/web/src/pages/home/model/browser/tool-protocol.ts` (module) — tool calling is prompted as plain text in the `<tool_call>` dialect Qwen, Hermes and SmolLM were trained on. WebLLM's own `tools` field is unusable here: it accepts five 8B Hermes builds only, forbids a system prompt beside the tools, and forces every answer through a JSON grammar, so a model could call a tool but never write the prose that follows. Prompting the protocol keeps one loop for every model.
- `apps/web/src/pages/home/model/browser/tool-protocol.ts › toChatMessages` — tool calls must be folded into the assistant's own text turn and tool results into a _user_ turn. That is the shape the models saw in training and the only one WebLLM's chat templates can render, since most of them have no `tool` role.
- `apps/web/src/pages/home/model/browser/language-model.ts › WebLlmLanguageModel.doStream` — `extra_body: { enable_thinking: false }` is required: otherwise Qwen3 thinks before every answer, about a minute per lookup on a laptop GPU, for a question the tools answer anyway.
- `apps/web/src/pages/home/model/browser/language-model.ts › WebLlmLanguageModel.doStream` — with thinking off, Qwen3 still writes an empty `<think>` block and a newline or two. A part holding only whitespace would render as "Thought" or as an empty answer row, so the first delta of a part is dropped when it trims to nothing.
- `apps/web/src/pages/home/model/browser/engine.ts › loadBrowserModel` — a second call while one is loading is ignored on purpose, because WebLLM serialises reloads on its own lock and two overlapping progress streams would fight over the same status. A device lost mid-load (usually out of memory) leaves the engine holding half a model, so the engine is unloaded before the error is reported, and a failed unload adds nothing to the error already in hand.
- `apps/web/src/pages/home/model/browser/engine.ts › useBrowserModel`, `useWebGpuSupport`, `model-choice.ts › useRememberedModel` — these stores must answer idle or `null` on the server and during hydration so the two renders cannot disagree. WebGPU support is the whole requirement for a browser model: no adapter, no browser model.
- `apps/web/src/pages/home/model/browser/models.ts › browserModels` — WebLLM publishes `vram_required_MB` measured at a 4096-token window, so the cost of the larger window this app asks for is added by hand. `KV_VALUES_PER_TOKEN` is sized for the largest attention stack in the catalog (Qwen3 4B and 8B: 36 layers, 8 KV heads, 128 dimensions, keys and values), so the allowance rounds up for every other family, and the f32 builds pay twice the f16 KV cost per token.
- `apps/web/src/pages/home/model/browser/models.ts › CATALOG` — WebLLM's prebuilt list holds over a hundred builds, most never trained to call a tool, so only families that follow the `<tool_call>` protocol are offered. A build the installed WebLLM no longer ships is dropped rather than offered, and a GPU without `shader-f16` gets the f32 builds.
- `apps/web/src/pages/home/model/browser/history.ts › fitHistory` — a hosted endpoint's window is large enough that the server replays the whole transcript, but `engine.ts › CONTEXT_WINDOW_SIZE` is 8192 (WebLLM defaults to 4096, which the system prompt and tool signatures outgrow within two lookups) and about three thousand of those tokens are already spent before the transcript starts, so a few lookup-heavy turns must shed the oldest ones or WebLLM refuses the request outright. Turns leave as question-and-answer pairs, oldest first, so the model never sees an answer without its question. `CONSERVATIVE_CHARS_PER_TOKEN` is 3 where real ratios run 3.5 to 4.5 for English prose and lower for JSON tool results, so the estimate errs towards dropping a turn early.
- `apps/web/src/pages/home/model/browser/transport.ts › createBrowserChatTransport` — this is the server route's loop run in the browser: WebLLM's model, the same oRPC procedures the screens call, and the finished turn written through `assistant.saveTurn`, so a turn answered here lands in the same transcript as one the hosted model answered. The transcript `useChat` holds _is_ the model's context; there is no server copy to rebuild it from without another round trip, which is why `reconnectToStream` resolves to `null`.
- `apps/web/src/pages/home/model/browser/transport.ts › sendMessages` — a stopped earlier turn can hold a tool call with no result, and replaying it would fail the request as it would on the server, so those parts are stripped before the window is fitted. The answer id is minted before the stream, as on the server, so the row the turn lands in carries the id the reader's retry will name.
- `apps/web/src/pages/home/model/browser/transport.ts › errorCode` — WebLLM names a context overflow in prose only, so the message is pattern-matched: the reader needs to hear "start a new conversation", not "try again".
- `apps/web/src/pages/home/model/execution.ts › ToolStatus` — `cancelled` is not a state the AI SDK ever writes. It means a call was still waiting when the stream ended, because the reader pressed Stop or the connection dropped.
- `apps/web/src/pages/home/model/answer-segments.ts › splitAnswer` — the answer text is re-split on every streamed chunk, so a fence still open at the end is a chart in progress, and a last line that could still grow into the `openui-lang` opener is held back rather than flashed as a code block. Line endings may be CRLF, since nothing between the provider and here normalises them, and `openui` is accepted as the shorter opener the model may drop to.
- `apps/web/src/pages/home/model/tool-details.ts › formatDay` — an ISO-shape check is not sufficient for a model-authored day: `2026-13-01` matches the pattern and `Intl.DateTimeFormat` throws on the resulting Invalid Date, so a stored bad day would throw on every reload. The `Number.isNaN(getTime())` guard beside the pattern test is what prevents that.

## Routing and SSR

- `apps/web/src/` (the Feature-Sliced Design root) — a route file under `app/routes/` declares routing and nothing else, so the screen it shows is a page slice that renders anywhere. `app/routes/_auth/budget/route.tsx › Route.validateSearch` therefore holds the search vocabulary both budget pages read, and `app/routes/login.tsx › loginSearchSchema` and `app/routes/_auth/settings.tsx › settingsSearchSchema` each own the `?error=<code>` a provider hands back: a failure after the redirect leg arrives as a search parameter, not as a refused request. A page reads that parameter by path (`useSearch({ from: "/login" })`) because `Route` lives in the other file.
- `apps/web/src/shared/api/budget-cache.ts › TRANSACTIONS_QUERY_KEY` — hand-built rather than taken from `orpc.budget.getTransactions.key()`, because the list is an infinite query and the key has to stay matchable by prefix. It sits in `shared` because invalidating it is what every writer of transaction data does, and a key owned by one page would be an upward import from the others.
- `apps/web/steiger.config.ts`, `apps/fumadocs/steiger.config.ts` — `bun run lint:fsd` must run from the app directory: steiger reads a config only when its directory is the working directory, and silently falls back to its own defaults otherwise, which passes while checking nothing.
- `apps/web/src/app/routes/__root.tsx › Route.beforeLoad` — the `viewer` is answered once per page load from the request's own cookies, so `/login`, `/onboarding` and `/_auth` can redirect before the first byte. In the browser it is deliberately `UNKNOWN_VIEWER`: after hydration the live session belongs to the browser, and a stale server answer would fight `AuthGate`.
- `apps/web/src/app/routes/login.tsx`, `onboarding.tsx`, `_auth/route.tsx › Route.beforeLoad` — each redirects a `guest` or a `member` only; `unknown` falls through on purpose to `AuthGate`, which holds the live session.
- `apps/web/src/features/auth-gate/ui/auth-gate.tsx › AuthGate`, `isSetupUnsettled` — the browser-side twin of the `instance` check in those guards. Sign-in lands with a client-side navigation, where `instance` is `unknown`, so the gate reads `instance.status` itself and sends a `member` or `onboarding` audience to `/setup` while setup is not complete. It holds every other redirect until that answer arrives: the onboarding status usually answers first, and routing on it alone flashes `/onboarding` before `/setup`. A server render that already answered `ready` skips the wait.
- `apps/web/src/app/routes/__root.tsx › Route.head` with `apps/web/src/shared/config/server-url.ts › publicServerUrlScript` — the script must be injected through `head` because it has to run before the module scripts: the API clients are built at module scope in the browser and read `window.__FREENARY_SERVER_URL__` from it. `PUBLIC_SERVER_URL` in the web server's environment therefore wins at request time and one image serves any deployment; unset, the build-time `VITE_SERVER_URL` stays in force. Client and server read the same value back, so the head matches on both sides of hydration.
- `apps/web/src/shared/config/server-url.ts › escapeForInlineScript` — `<` cannot appear raw in an inline `<script>`, even inside a string literal, because the HTML parser ends the element at `</`. The URL is `JSON.stringify`d with `<` rewritten to `\u003c`.
- `apps/web/src/shared/lib/is-server.ts › isServer` — `import.meta.env.SSR` is a Vite build-time constant (verified: it inlines to `true` in the SSR build and `false` in the client build), so the environment is decided at import time instead of probed with `typeof window`.
- `apps/web/src/**` (every `Record<K, () => string>` message table: `pages/budget/model/period.ts`, `pages/budget/model/recurrence-labels.ts`, `pages/home/model/tool-labels.ts`, `pages/home/model/tool-details.ts`, `entities/category/model/taxonomy-labels.ts`, `app/shell/nav-items.ts`, `app/shell/first-steps.ts`, `shared/auth/auth-error-message.ts`, `shared/auth/oauth-callback-error.ts`, `pages/settings/model/security-error-messages.ts`, `pages/settings/model/category-appearance-labels.ts`) — the tables hold message _functions_, never their results, and `auth/auth-schemas.ts › emailField` is built per call for the same reason. A module is evaluated once per server process, so a called message would pin the first request's locale and serve it to every later render; switching locale reloads the document, so a mount is always a fresh locale. The `satisfies` clause is what turns a new enum member or taxonomy slug into a compile error rather than a blank label.
- `apps/web/src/server.ts › default.fetch` — `paraglideMiddleware` puts the request's locale in async storage before the render runs, so `getLocale()` returns the visitor's language during SSR; without it the first paint is always the base locale and then swaps. `LOCALE_VARY_HEADERS` is needed because the same URL answers in different languages, and unauthenticated pages such as `/login` are cacheable, so a proxy would otherwise serve one visitor's language to the next.
- `apps/web/vite.config.ts › paraglideVitePlugin` — locale lives in a cookie, not the URL: every route is behind auth, so localized paths would buy no SEO and cost a router rewrite. The `dev` script in `apps/web/package.json` repeats these same options because Vite caches the first failed resolution of `@/paraglide/server.js`, so `outdir` must exist before Vite starts; `project.inlang` would be the drift-proof home for them, but inlang's `.gitignore` there keeps everything but `settings.json` out of the repo.
- `apps/web/src/app/routes/callback/$provider.tsx › Route.ssr` — `ssr: false` is required, because exchanging the provider's callback needs the session cookie, which only the browser holds.
- `apps/web/src/app/routes/callback/$provider.tsx › callbackSearchSchema` with `pages/callback/api/exchange-callback.ts › parseCallbackDestination` — providers append their own query parameters and TanStack Router auto-parses JSON-shaped and numeric values, so each value is normalised back to the exact string the provider sent: only the provider's own adapter knows what it means. A failed exchange never got far enough to report where it came from, so the destination is read off the _unverified_ `state`, which is safe only because it picks between two of our own pages and anything unexpected lands on onboarding. An `error` parameter means the reader declined at the bank, and the provider still echoes `state`, so the flow can still return where it started.
- `apps/web/src/pages/budget/model/search.ts › budgetSearchSchema` — a URL carries whatever the sender typed and the router JSON-parses it, so every field reads through a parser that answers "absent" instead of throwing: a mangled link must open the default view, never a route error. Nothing defaults in the schema, so an absent parameter means the default, a clean view keeps a clean URL, and a shared link carries only what its sender changed. The `r`-prefixed fields belong to Recurring and the rest to Transactions. `MAX_PICKABLE_MERCHANTS`, `MAX_PLAUSIBLE_AMOUNT` and `EARLIEST_PLAUSIBLE_YEAR` bound what a hostile link may ask of the database, since merchant keys are bank text rather than a vocabulary this app owns.
- `apps/web/src/pages/budget/ui/budget-area.tsx › Route.search` — a sidebar link carries no search of its own and the router would answer that with an empty one, so the budget area needs `retainSearchParams(true)`: both budget pages read one vocabulary, and stepping between them must keep the view the reader built.
- `apps/web/src/pages/budget/ui/recurring-page.tsx › RecurringPage` — `asOf` comes from the server's `data.asOf`, when detection ran, and never from a render-time clock, which would move every projection between two renders. The view also reads a fixed trailing year on the server rather than the period the Transactions view carries, and `m.budget_recurring_scope()` is the string that says so.
- `apps/web/src/pages/brand-avatar/ui/brand-avatar-page.tsx` — the whole route is a temporary dev-only state board: not linked from the app, not in the message catalogs, and meant to be deleted.

## Client data

- `apps/web/src/shared/api/orpc.ts › createQueryClient` — the cache reports only failures a mounted component observes, so a prefetch nobody is watching raises no toast. `budget-queries.ts › warmWithoutRaising` depends on that: it settles rather than awaits, so a failed warm-up rejects nothing either.
- `apps/web/src/pages/budget/api/budget-queries.ts › TRANSACTIONS_QUERY_KEY` — hand-built rather than taken from `orpc.budget.getTransactions.key()`, because the list is an infinite query and the key has to stay matchable by prefix. `shared/api/budget-cache.ts › invalidateBudgetData` and `pages/budget/model/use-transaction-category.ts` both match it by prefix, and `orpc.budget.key()` cannot — which is why `invalidateBudgetData` issues a second invalidation.
- `apps/web/src/pages/budget/api/budget-queries.ts › prefetchTransactions` — the 60 s `staleTime` that `createQueryClient` sets for every query makes a repeat a no-op, so a pointer resting twice on the same control costs one request.
- `apps/web/src/pages/budget/ui/budget-area.tsx › BudgetArea` — the area renders nothing until the accounts query answers: painting the budget or the empty state and then swapping it is worse than the shell standing alone for a beat.
- `apps/web/src/pages/onboarding/ui/onboarding-page.tsx › BANK_STEP_INDEX` — the institutions prefetch stays enabled at step 1 even when the banking provider reports itself unavailable, so a flow resumed into the bank step still has its bank list.
- `apps/web/src/pages/budget/model/use-account-sync.ts › refetchInterval` — the status poll runs only while a run is known or a sync request of this tab is in flight, so an idle budget page issues no traffic at all. The cost is that a run somebody else starts is invisible to an idle page until it fetches for another reason, which is why the mutation invalidates the status query in `onMutate` rather than waiting for its own answer.
- `apps/web/src/pages/budget/model/use-account-sync.ts › TRANSACTIONS_PER_REFRESH` — refreshing the lists on every poll would re-run five aggregate queries every 1.5 s for the length of an import. The effect keys on `phase` plus the imported count divided by a hundred, so the page refreshes on a phase change, on the run ending, and once per hundred transactions that land.
- `apps/web/src/shared/api/budget-cache.ts › invalidateBudgetData` — the sync status is excluded from the budget invalidation. It is a poll with its own cadence, and invalidating it from the refresh it just triggered adds a request per hundred transactions and tells nobody anything new.
- `apps/web/src/pages/budget/model/sync-progress.ts › syncProgressShape` — importing has no percentage on purpose. The account count is known only after each provider answers and says nothing about the transactions behind it, so a bar built on it would sit at zero through the whole of a one-account import. Categorisation knows its total before it starts, so that phase is determinate.

## Auth client and settings

- `apps/web/src/shared/auth/auth-client.ts › AUTH_MOUNT_PATH` — better-auth derives its route matching from the _path_ of `baseURL`, so the public auth path must equal the server-side mount. Both are `/api/auth`.
- `apps/web/src/shared/auth/auth-client.ts › authClient.plugins` — `emailOTPClient` is present for address confirmation and password reset only; the server refuses `/sign-in/email-otp`, because every account signs in with a password. Google, Apple and the generic OIDC provider all go through `signIn.social`: the generic-oauth plugin registers itself as a social provider, so it needs no client counterpart.
- `apps/web/src/shared/auth/oauth-callback-error.ts › MESSAGE_BY_CODE` — Better Auth reports a failure that happens _after_ the redirect leg by sending the browser back to `errorCallbackURL` with `?error=<code>`, not by refusing the request that started it. Nothing else surfaces these, so a screen that ignores the query parameter shows a silent bounce — which is why `error` is part of the `login.tsx` and `_auth/settings.tsx` search schemas. The parameter carries three kinds of value: Better Auth's own `OAUTH_CALLBACK_ERROR_CODES`, its free-form linking failures with spaces turned into underscores (`account_not_linked` means a row already exists for that address but is unconfirmed), and whatever OAuth error the provider itself sent.
- `apps/web/src/pages/login/lib/auth-error-message.ts › AuthRequestError` — the interface deliberately has no `message` field. The server's own wording is untranslated and, on a sign-in screen, can say more about an account than an unauthenticated caller may learn, so it is never rendered.
- `apps/web/src/shared/auth/credentials.ts › otpField`, `passwordField` — a length bound is only ever the server's own, published on `auth.capabilities`. With no bound the screen checks presence only: a floor of this screen's invention would reject a code the server would have accepted, or lock out an existing password that predates today's minimum.
- `apps/web/src/pages/settings/model/security-error-messages.ts › PASSKEY_MESSAGES` — `SESSION_NOT_FRESH` reuses the linked-account wording because registering a passkey sits behind the same freshness window as `/link-social` and `/unlink-account` (`packages/auth/src/index.ts` sets `freshAge` to the full session expiry). A dismissed WebAuthn prompt is deliberately absent from the table: `hooks/settings/use-passkey-actions.ts` drops it before asking for a message, because the reader already knows they cancelled.
- `apps/web/src/pages/settings/ui/settings-page.tsx › SettingsContent` — `hasPassword` is deliberately tri-state (`boolean | undefined`). A section that read "no password" from an unanswered or failed account list would tell every password user something false and hide the only fix.
- `apps/web/src/pages/settings/model/user-agent-device.ts › DEVICE_PATTERNS_NARROWEST_FIRST` — order is the whole trick: an Android user agent also claims "Linux", ChromeOS claims both, and an iPad in desktop mode claims "Macintosh", so the narrower family must be tested first.
- `apps/web/src/pages/settings/model/category-sections.ts › toCategorySections` — a heading names its own items rather than the whole radio group, so empty sections are dropped and no heading survives without something under it. The headings are the three flow sections plus one per top-level custom category, so a reader picking a budget line reads `Income`, `Savings & investment` and `Spending` rather than sixteen topics. A heading-less section takes its own entry's key, because several top-level custom categories can coexist and would otherwise collide inside one radio group. Matching runs on the _translated_ label (as it does in `budget/category-search.ts`) and through `search-text.ts › foldForSearch`, because translated lists are full of accents a keyboard does not reach for: "bresil" has to find "Brésil".
- `apps/web/src/features/bank-connection/model/bank-rows.ts › buildBankRows` — one row per _connection_ rather than per institution: a connection whose institution the provider no longer lists would otherwise have nowhere to be disconnected from, and it falls back to the stored `institutionName`. Connected banks come first so they are reachable without searching.
