# API package

Durable facts that the code cannot carry in a name. Each bullet names the module it belongs to. Source: comments deleted when the `no-comments` rule was adopted.

The reader-facing contracts live in the documentation site and are not repeated here: [bank-provider.md](./bank-provider.md) owns the `BankingProvider` boundary, and [`reference/api.mdx`](../../apps/fumadocs/content/docs/next/reference/api.mdx) with [`reference/procedures.mdx`](../../apps/fumadocs/content/docs/next/reference/procedures.mdx) own the public route surface, the caps and the error codes.

## Routers and the request boundary

- `apps/server/src/index.ts › /api-reference*` — the handler rebuilds the request on `BETTER_AUTH_URL` before oRPC sees it. `OpenAPIReferencePlugin` builds `servers[0].url` and the spec URL in the docs page from `request.url.origin`, which behind a TLS proxy is `http://`, and behind the web app's forwarder is the Docker-internal `http://server:3000`.
- `packages/api/src/routers/auth.ts › accountExists` — the endpoint deliberately leaks whether an address has an account, because the sign-in form cannot branch without it. The per-caller `ACCOUNT_EXISTS_RATE_LIMIT` is the mitigation, not a nicety.
- `packages/api/src/routers/auth.ts › accountExists` — Better Auth stores email addresses lowercased, so a mixed-case entry must be folded before the lookup or the form offers sign-up for an account that exists.
- `packages/api/src/routers/auth.ts › viewer` — public on purpose: a guest is an answer, not a refusal. It returns `sessionCookieShared` because without it `guest` only means "unreadable from this origin", which is what the web app's own server needs before it redirects.
- `packages/api/src/lib/rate-limit.ts › callerBucket` — caller identity is Better Auth's own resolution (`getIP(headers, auth.options)`), which reads only the configured header, refuses an untrusted forwarded chain, and collapses IPv6 to a subnet. A caller it cannot place shares the single `untrusted` bucket rather than minting one per request: a spoofable leftmost-hop read would make every cap decorative.
- `packages/api/src/lib/rate-limit.ts › consumeRateLimit` — must stay one SQL statement. The read, the window reset and the increment have to be atomic, or concurrent callers all pass on a stale count. It counts in the same `rate_limit` table Better Auth's own limiter uses.
- `packages/api/src/routers/bank-connection.ts › disconnect` — provider revocation is asked for first so the bank-side consent stops too, but a failure there must never block a user from deleting their data, hence `revocationRequested` rather than a throw. `_count.accounts` is read before the delete because the FK cascade takes the accounts, transactions and holdings with the connection.
- `packages/api/src/lib/transaction-filter-conditions.ts › companyIsNoneOf`, `categoryIsNoneOf` — an exclusion is spelled out branch by branch rather than as `NOT` over the inclusion. SQL compares a `NULL` column to `NULL`, `NOT NULL` is still `NULL`, and the row drops: `NOT (counterpartyName ILIKE 'amazon' OR …)` would hide every transaction whose bank sent no counterparty. Each branch pins the column's nullness first, so a nameless or uncategorised row survives an `is not`, and `uncategorised` also covers a row that neither the user nor the pipeline categorised. The test evaluates the built condition with SQL's three-valued logic for that reason.
- `packages/api/src/routers/saved-filters.ts › saveFilter` — a name is unique per user through `citext`, so saving under a name that differs only in case replaces that row, and the cap of `MAX_SAVED_FILTERS` counts only when the name is new. The cap is soft: the count and the upsert run at READ COMMITTED, so two saves of new names at once can both pass it, and two first saves of one name can race on the unique index and fail one request. `listSavedFilters` reads `filters` back through `lenientTransactionFiltersSchema`, so a stored filter that a later schema refuses drops instead of failing the list.
- `packages/api/src/lib/transaction-amount-bounds.ts › amountBoundsCondition` — the bounds constrain how much money moved, not the signed amount, so a floor of 5000 means fifty euros in either direction. Each branch pins its own sign: a lone ceiling on the incoming branch would otherwise read `amount <= 3000` and let every outgoing row through.
- `packages/api/src/routers/settings.ts › deleteCustomCategory` — `BudgetLine.category` is `onDelete: Restrict` while `CustomCategory.parent` is `onDelete: Cascade`, so the children go with the row and every line whose `categoryId` is the row _or any child_ has to be reassigned inside the same transaction, before the delete, or the constraint refuses. A line must land on a category, so the target is the parent group's catch-all (`CATEGORY_GROUP_FALLBACKS`), else `uncategorised` — which is what a subcategory always gets, because its own `parentSlug` is null. `deletedSubcategories` is reported because the reader is told how many rows one confirmation removed.
- `packages/api/src/routers/settings.ts › listCategories` — the emitted order is a contract, not a presentation choice: `apps/web` assembles its tree by reading the flat array in order, where an `isGroup` entry opens a group and every following non-group entry belongs to it. The order is, per predefined group, the group, then its predefined categories, then the user's customs nested in it; then each top-level custom category in `sortOrder`, each followed by its own subcategories in `sortOrder`. Reordering the emission silently reparents rows in the interface. A custom row whose stored `parentSlug` decodes to no known group appears in neither pass and is omitted, which predates nesting.
- `packages/api/src/lib/categories.ts › customCategoryColor` / `customCategoryPickedColor` / `customCategoryDisplayColor` — the colour states the direction of money, so a custom category nested under a group is painted that group's colour, and one nested under another custom category is painted that parent's stored choice when that value is in the palette. `customCategoryDisplayColor` hands `parentChosenColor` to `customCategoryPickedColor` rather than return the raw column, so an unreadable stored value falls back to `grey` on the child exactly as it does on the parent and the child never shows a colour the parent does not; it falls through to `customCategoryColor` only when there is no custom parent. The entry therefore carries two: `color` is what every surface paints, and `pickedColor` is the choice still stored on the row. Both are needed, because `apps/web/src/pages/settings/model/category-sections.ts › editedOf` seeds the edit drawer from the entry and `updateCustomCategory` writes `input.color` back unconditionally — seeding from `color` would persist the parent's colour and destroy the choice on the first rename, and again on the promotion that is supposed to reveal it. Seeding from `pickedColor` is what makes the choice survive until the category is top-level again.

## Budget aggregation and persistence

- `packages/api/src/routers/budget.ts › aggregateOutgoing` — only months that carry at least one transaction count towards an average or a median, so months before the bank was connected do not dilute the result.
- `packages/api/src/routers/budget.ts › outgoingByCategory` — the per-category aggregate is the primitive, and every consumer folds it up from there rather than aggregating its own grouping. `getSankeyData` folds it into groups after the fact, because a median of medians is not a group's median.
- `packages/api/src/routers/budget.ts › getSankeyData` — a group's value is the sum of its categories even under median, because every ribbon out of a group node must add up to the node itself. Groups keep taxonomy order so the column reads the same in every period; categories within a group lead with the largest.
- `packages/api/src/routers/budget.ts › getFixedVsVariable` — the split decomposes the breakdown's own per-category aggregate, which is why the breakdown, the budget-vs-actual comparison and this split reconcile. The variable side is derived by subtraction so the pair sums to the total whichever way per-category rounding went; aggregating a fixed and a variable series apart would not, because a median is not additive.
- `packages/api/src/routers/budget.ts › getFixedVsVariable` — a cadence is judged from the year on each side of the period (`cadenceWindow`), so the first months of a history do not read their rent as variable.
- `packages/api/src/routers/budget.ts › getBudgetVsActual` — a declared plan is monthly, so only a period _total_ scales it up (`planScaleMonths`); the average and median aggregations are already per-month figures, and `getRecurring`'s `plannedOutgoingMinor` needs no scaling for the same reason.
- `packages/api/src/routers/budget.ts › getRecurring` — monthly income divides by the months since the first income row (`monthSpan`), not by a fixed twelve: a first import reaches back 90 days, and dividing a quarter of a year by twelve would report a quarter of the reader's real income.
- `packages/api/src/routers/budget.ts › getCashFlow` / `getMerchants` — `$queryRawUnsafe` is safe here because every interpolated fragment comes from a closed, code-owned table (`CASH_FLOW_GRAINS`, `AMOUNT_SIGN_PREDICATE`), and every user value is a positional parameter.
- `packages/api/src/routers/budget.ts › getMerchants` / `getTransactions` — one company is one row whichever column named it: the grouping key is the case-folded `COALESCE(counterpartyName, normalisedDescriptor)`, and `getTransactions` matches both columns case-insensitively. Otherwise a bank that names a merchant on its direct debits and nobody on its card rows splits into two entries that each return the other's transactions. `initcap` gives a descriptor the case a name has, and `MIN` picks one spelling per key so the row is stable between calls.
- `packages/api/src/routers/budget.ts › clearResolutions` — drops the pipeline's own verdicts so the next batch re-decides them. Manual overrides (`categoryOverride`) and internal-transfer flags are the user's, not the pipeline's, so they survive.
- `packages/api/src/routers/budget.ts › syncAccounts` — a forced sync re-reads the provider's whole window and clears resolutions first. Its purpose is key repair, not completeness: re-importing re-derives the merchant key of every row it touches, and a row already carrying a resolved category would otherwise never be read against the new key.
- `packages/api/src/lib/bank-sync.ts › PROVIDER_SERVED_HISTORY_DAYS` — bank providers serve roughly 90 days of transaction history. That is both how far back a sync with nothing to resume from reaches and the whole of what a forced re-read can recover; asking for more returns nothing.
- `packages/api/src/lib/bank-sync.ts › importAccountsInSeries` / `upsertTransactionsInSeries` — accounts are synced one at a time, and so are each account's transactions, to stay inside provider rate limits and to avoid unique-constraint races on `Transaction(accountId, providerTransactionId)`. `Effect.forEach` is left at its sequential default, so adding a `concurrency` option here changes behaviour.
- `packages/api/src/routers/budget.ts › writeResolutions` / `syncEveryConnection` — one failure must not abort the batch: a failed resolution write counts as zero, and a connection whose provider the registry no longer knows records its message in `errors` instead of costing every other bank its sync.
- `packages/api/src/lib/bank-provider-user.ts › ensureProviderUser` — two tabs starting a connection at once each create a provider user, so the insert can lose a unique-constraint race (Prisma `P2002`). The stored row wins, and the duplicate is deleted at the provider (best effort, through `deleteUser`) because it holds no data yet; that case is the tagged error `ProviderUserAlreadyStored`, and any other Prisma failure is rethrown as the original error object.
- `packages/api/src/lib/bank-provider-user.ts › findProviderUser` / `releaseProviderUser` — the core owns the identity row so adapters stay free of the database, and the identity outlives every individual connection. Deleting it at the provider is best effort: the local row goes either way, because a provider that refuses must not leave a dangling identity behind. The row goes through `deleteMany`, so a second disconnect racing the first finds nothing to delete instead of failing with `P2025`.
- `packages/api/src/lib/budget-planned.ts › AVERAGE_MONTH_MS` / `monthSpan` — 30.436875 days is the mean Gregorian month, chosen so a whole-month span rounds to exactly its own month count. Counting calendar keys instead would miscount: the client sends local month boundaries, so a UTC server reads `from` as the previous month and doubles a one-month plan.
- `packages/api/src/lib/budget-planned.ts › categoryOfCategoryRef` / `plannedByCategory` — a budget-vs-actual row is keyed by category now, but a custom category is not one, so a line on `custom:<id>` contributes to its parent group's fallback (`CATEGORY_GROUP_FALLBACKS`). That is the same target `settings.deleteCustomCategory` moves a line to, which is why deleting a custom category never moves money between rows of the chart. `GROUP_OUTSIDE_THE_TAXONOMY` is `spending`, so a line whose parent slug decodes to nothing still lands on the outgoing side rather than on a group that no longer exists.
- `packages/api/src/lib/budget-profile.ts › MAX_AMOUNT_MINOR_UNITS` — 2_147_483_647 is not a product choice: `BudgetLine.amount` is a Postgres `INTEGER`, so a larger value fails at insert time rather than at validation time. The bound is shared by the router that validates a save and the editor that blocks one.
- `packages/api/src/lib/sync-progress.ts › claimSyncRun` — the run row is the lock, not a progress display that happens to exist: a reload mid-sync used to start a second full provider read. The claim is one conditional `updateMany` plus a `createMany` with `skipDuplicates`, so two tabs racing at the same millisecond still leave one winner without a transaction. It returns the `startedAt` it wrote, which is the identity of the claim.
- `packages/api/src/lib/sync-progress.ts › createSyncReporter` — the counters live in the closure and every write sends the whole snapshot scoped to `{ startedAt: claimedAt, userId }`. A dropped write therefore costs nothing, no increment can race, and a reporter whose row was reclaimed writes nothing at all — without that scope its `finished()`, which `Effect.ensuring` always reaches, would clear the lock of the run that replaced it and let a third sync start against the same provider. The write throttle (`PROGRESS_WRITE_INTERVAL_MS`) is what lets `upsertTransactionsInSeries` report every single row; phase changes and account boundaries bypass it, because a reader waits on those.
- `packages/api/src/lib/sync-progress.ts › SYNC_RUN_ABANDONED_AFTER_MS` — a process killed mid-sync leaves its row in `IMPORTING` for ever, which would freeze the progress indicator and refuse every later sync. Five minutes is above the longest silent stretch a run has and below a reader's patience. Keeping that true is what `heartbeat` is for: the classification pass can spend minutes inside `categoriseBatch` on provider calls, so it reports after each merchant signature it settles. It is a read-side rule as much as a claim-side one: `syncProgressFrom` reports an abandoned run as no run.
- `packages/api/src/routers/budget.ts › categoriseUncategorised` — `categorisedTotal` counts every candidate row, so the rows the pipeline decided _not_ to resolve are reported too, before the writes begin. Counting only the resolutions would divide two different populations and leave the bar short of its end on every batch with an unresolved row in it.
- `packages/api/src/routers/budget.ts › syncAccounts` / `recategorise` — the run ends whatever happens, including a defect from Prisma: `recategorise` through `Effect.ensuring`, `syncAccounts` through `Effect.matchCauseEffect`, and everything after the claim sits inside the guarded effect. A `clearResolutions` left outside it would strand the claim for the whole abandon window when it failed.
- `packages/api/src/routers/budget.ts › syncAccounts` — the sync runs in a fiber of its own (`Effect.runFork`) and the request answers with the claim's `startedAt` (issue #205). A sync with a slow provider or a long categorisation outlasts any proxy timeout, so holding the request open made the caller wait for nothing it could not read from `getSyncStatus`. The outcome a caller used to read from the response is stored in `SyncRun.failures` by `finishedWith`, and `getSyncOutcome` returns it for that `startedAt` only. A run that crashed ends through `finished`, which leaves `failures` null, so the caller gets an error rather than a success nobody earned. A process that stops mid-sync loses the run, and the abandon window frees the claim.

## Category taxonomy

- `packages/api/src/lib/taxonomy.ts` — one flat category set, read by categorisation, budgeting and the Sankey so the three cannot disagree. `SpendingCategory` covers income as well as spending, because a cash flow only balances if money in and money out share one vocabulary. A group is a section of that flow (`income`, `investments`, `spending`) and never a topic: a topic taxonomy forced every signal to guess which of sixteen shelves a merchant belonged on, and the reader to learn them.
- `packages/api/src/lib/taxonomy.ts › CATEGORY_ICON_NAMES` — a contract with `apps/web`, enforced by `satisfies Record<CategoryIconName, …>` in `apps/web/src/entities/category/ui/category-icon.tsx` and `apps/web/src/pages/settings/model/category-appearance-labels.ts`. Adding a name here is a two-package change, and the web type-check is what refuses a half-done one.
- `packages/api/src/lib/taxonomy.ts › categoryColor` / `CATEGORY_PALETTE_SLOT_OF` / `CATEGORY_ICONS` — the icon is per category, and so is the colour a category shows. `CATEGORY_PALETTE_SLOT_OF` gives each built-in category a fixed slot of a categorical palette: eight hues (blue, orange, teal, pink, purple, yellow, green, brown) in a base and an `-alt` tone, plus `grey`, which only `uncategorised` uses. No two categories of one group share a slot, and nothing about rank, amount or period moves a category off its slot. Red is not a slot, because budget-vs-actual paints an over-plan bar with `--destructive`. The slot rides on `CategoryAppearance.slot` and `CategoryEntry.slot`, and `CategoryIcon` prefers it over `color`. `categoryColor` still answers the group's colour, `CATEGORY_GROUP_COLORS[CATEGORY_GROUP_OF[category]]`, which is what group headers, custom categories nested under a group, and the group nodes of both Sankeys show. An earlier rule shaded the group colour by the place of a category in its group; sixteen tints of one blue could not be told apart, which is what #72 replaced. The tokens are `--category-<slot>` in `packages/ui/src/styles/globals.css`, one set per theme, each at 3:1 or more against `--card`.
- `packages/api/src/lib/taxonomy.ts › CATEGORIES_BY_GROUP` / `SPENDING_CATEGORIES` — `SPENDING_CATEGORIES` is _derived_ by concatenating the three group arrays, which is what makes the contiguous run per group structural rather than a convention a reviewer has to police. The group order is flow order, not alphabetical: `income` first because it is the Sankey's left column, then the two allocation sections in the order a budget is declared. Within a group the order is display order for the pickers.
- `packages/api/src/lib/taxonomy.ts › CATEGORY_DIRECTION_OF` / `categoriesForDirection` — the direction lives on the category because the sign of a transaction already decides it: offering `salary` on a card payment was the single largest source of wrong picks. `categoriesForDirection` is precomputed at module load for both directions, because the transaction drawer calls it per render. `people`, `cash-withdrawal` and `uncategorised` carry `both`: lending and repaying, cash out and cash back in, and an honest "no idea" all run either way.
- `packages/api/src/lib/taxonomy.ts › isSpendingCategory` / `isCategoryGroup` — a slug must never be both a group and a category: a budget line stores one slug and the pickers key their React lists by it. That is why `packages/api/src/lib/categories.ts › parseCategoryKey` rejects a group slug, while a _custom_ top-level category stays assignable — it holds no categories of its own to pick instead. It is also why the `investments` group and the `securities` category do not share a name, even though the reader sees `Savings & investment` over `Investments`.
- `packages/api/src/lib/custom-category-parent.ts › resolveCustomCategoryParent` — `parentSlug` and `parentId` are mutually exclusive and no `CHECK` constraint says so: `createCustomCategory` and `updateCustomCategory` read one `parentKey` field and derive exactly one of the pair from it, so no input shape can set both. Those two procedures are the only writes of the pair, and both take it from `routers/settings.ts › resolveParentOrRefuse`, which is also the one place a refusal becomes an `ORPCError` (`PARENT_REFUSAL_ERRORS`). Nesting stays one level deep from two refusals rather than a depth count: a parent must be top-level (`parent-is-nested`), and a row that already has children is refused any parent at all (`would-nest-a-parent`). Both judge one read of the caller's own rows, so they hold only while nothing writes between that read and the write: two concurrent updates, each naming the other as its parent, would otherwise both pass, and a create that nests a child under the row an update is re-parenting would slip past `would-nest-a-parent`. Either outcome takes rows out of the interface, because `listCategories` emits a custom entry only under a group or under a top-level parent, while their budget lines still point at them. Every write of the pair therefore runs in one `$transaction` that opens with `routers/settings.ts › lockOwnCategories` (`SELECT "id" FROM "custom_category" WHERE "userId" = … FOR UPDATE`), and the `findMany` that follows it is the rule's whole input. `deleteCustomCategory` takes the same lock, so a create cannot add a child between its read of `children` and the cascade: the count it reports would be short by one, and a line on that child would meet `BudgetLine.category`'s `onDelete: Restrict` as a raw constraint violation. A caller is serialised against themselves, which is why nothing walks the ancestor chain. The rule takes those rows rather than a Prisma client or a caller-computed flag, and reads both facts off them — which row is top-level, and whether any row names `categoryId` as its parent — so a create, whose `categoryId` is null, holds no subcategories by construction and every refusal is unit-testable on its own.
- `packages/api/src/lib/taxonomy.ts › LEGACY_CATEGORY_SLUGS` / `LEGACY_CATEGORY_GROUPS` / `CATEGORY_GROUP_FALLBACKS` — 70 old slugs and 14 old group names, covering both the two-level hierarchy and the flat set that preceded it. No data migration rewrites a stored slug, so the decoder is the only thing that keeps an old value readable: `dictionary.ts › indexMerchantLine` runs every label of the prebuilt artifact through `resolveCategorySlug` and silently drops the row when it answers null, and the shipped merchant dictionary still spells 11,356 merchants the hierarchy way. A slug that carried _more_ precision than the new set collapses into it (`flights`, `accommodation` and `taxi` all land on `transport-travel`); one that carried less lands on its group's fallback, because it never held the precision the new set asks for.
- `packages/api/src/categorisation/user-override.ts › lookupUserOverride` — the one read that used to cast `merchant_override.category` straight to `SpendingCategory`. Nothing rewrites that column, so the cast was unsound the moment the taxonomy changed under it; it resolves through the decoder now and returns null on a value it cannot read, which lets the pipeline fall through to the next stage instead of handing an unknown key to `categoryLabel`.
- `packages/api/src/lib/mcc-categories.ts › FIRST_ISSUER_ASSIGNED_TRAVEL_MCC` / `LAST_ISSUER_ASSIGNED_TRAVEL_MCC` and `MCC_TO_CATEGORY` — the ISO 18245 `3xxx` block is issuer-assigned per carrier in three runs (3000–3299 airlines, 3300–3499 car rental, 3500–3999 lodging). All three are `transport-travel` now, so the three ranges collapsed into one bound pair and an off-by-one inside the block costs nothing. Three individual readings the table cannot state by itself: `4582` is airport and terminal charges rather than the ticket, and both are travel anyway; `5983` fuel dealers deliver heating oil, wood and LPG to the home, which is `bills-utilities` rather than `car-fuel`; `6010` is a manual cash disbursement over a counter, so `cash-withdrawal`, while `6012` is the bank selling a service, so `loans-bank-fees`.
- `packages/api/src/categorisation/deterministic.ts › readsAsRefund` — on a credit, a keyword match survives only when its category can run that way. The test is the category's own direction: a match whose direction is `out` means a refund rather than that category, so the match is refused. A direction of `in` or `both` is kept, which is how `people`, `cash-withdrawal` and `uncategorised` reach a credit at all.
- `packages/api/src/lib/taxonomy.ts › TAXONOMY_VERSION` — `2`. It is inside the classification signature (`classifier/signature.ts`), so a stored answer of the previous label space is never decoded into the new one. Replacing the set is exactly the case the version exists for; bump it whenever a slug is added, removed or re-parented.

## Bank providers

- `packages/api/src/providers/types.ts › ProviderTransaction.bankTransactionFamilyCode` — the ISO 20022 family code where the provider exposes or derives one. `bankTransactionDescription` is the ASPSP's own proprietary free-text classification instead, and `bank-sync.ts › mapProviderFields` writes _that_ one into the `bankTransactionCode` column.
- `packages/api/src/providers/types.ts › BankingProvider.closeConnection` — resolving means the deletion request landed and no more: banks confirm nothing further, and the consent may outlive it. Both adapters therefore treat a 404 as success (`powensDeleteIfPresent`, `ebDeleteIfPresent`).
- `packages/api/src/providers/types.ts › BankInstitutionsUnavailable` — a failed institution call and a country with no bank used to be the same empty array, so a partial bank list read as complete. Both adapters now fail the `Effect` with this tag instead, `routers/bank-connection.ts › listInstitutions` catches it per country into `unavailableCountries`, and the two single-country call sites map it to `SERVICE_UNAVAILABLE` rather than to "unknown institution". `LIST_INSTITUTIONS_CONCURRENCY` and `lib/country-code.ts › MAX_TAX_RESIDENCY_COUNTRIES` bound what one request can fan out to the provider.
- `packages/api/src/providers/powens/client.ts › PowensAccountTypeSchema` — Powens documents the account type as `{ name }`, but some domains send a bare string. The schema is a union so both shapes decode.
- `packages/api/src/providers/powens/client.ts › PowensConnectionSchema.state` — `null` means healthy; any other value names why the connection stopped. Only the values in `powens/index.ts › STATES_ONLY_THE_ACCOUNT_HOLDER_CAN_CLEAR` fail a sync; every other state (a sync in flight, a bank-side outage) is transient and left to the next retry.
- `packages/api/src/providers/powens/client.ts › fetchTransactionPages` — `limit` is mandatory on the Powens transactions endpoint and caps at 1000 (`MAX_TRANSACTIONS_PER_PAGE`), and `last_update` is the cursor. The pagination link `_links.next.href` is an absolute URL rather than a path, so the loop hands it straight to `requestJson` and bypasses `powensUrl`'s base.
- `packages/api/src/providers/powens/index.ts › completeConnection` — a connection belonging to another Powens user answers 404 under this user's token. That 404 _is_ the ownership check on the callback; there is no second one.
- `packages/api/src/providers/powens/index.ts › startConnection` — passing exactly one `connector_uuids` value skips connector selection in the webview, which then handles credentials, SCA and which accounts the user activates.
- `packages/api/src/providers/enable-banking/client.ts › LITERAL_NEWLINE_ESCAPE` — `ENABLE_BANKING_PRIVATE_KEY` usually arrives with literal `\n` sequences instead of real newlines (env files, CI secrets), so the key is un-escaped before it is used to sign.
- `packages/api/src/providers/enable-banking/client.ts › LONGEST_HISTORY_STRATEGY` — `strategy=longest` is sent on the first page only; it asks the ASPSP for the longest cold-start history it will give.
- `packages/api/src/providers/enable-banking/map-transaction.ts › deriveFingerprint` / `mapEBTransactions` — the `stableFields` key names, their order and their values are a persisted hash input: changing any of them re-keys every `derived:<hash>:<n>` `providerTransactionId` and duplicates the account's history on the next sync. `entry_reference` is the authoritative identity when present; `transaction_id` is volatile between calls and is excluded from the fingerprint on purpose, and `remittance_information` is sorted before hashing because a provider does not guarantee the order of `remittanceLines`.
- `packages/api/src/providers/enable-banking/map-transaction.ts › parseMinorUnits` — amounts arrive as decimal strings and are combined digit-wise into an integer so no float rounding drift is possible. A leading `-` in the string keeps the amount negative, whatever the indicator says; an unsigned amount takes its sign from `credit_debit_indicator`. `balance_after_transaction` carries no indicator, so an overdrawn balance relies on its own `-`.

## Assistant

- `packages/api/src/assistant/handler.ts › streamText` — `instructions`, not a system message: `ai@7` refuses a `system` role inside `messages` outright. Without `abortSignal`, the SDK never reports an abort when the reader presses Stop or closes the tab, and a half-turn gets stored.
- `packages/api/src/assistant/handler.ts › questionSchema` — a posted `file` part with no `url` throws inside `convertToModelMessages` instead of answering 400, which is why the question schema admits text parts only.
- `packages/api/src/assistant/handler.ts › admitChatRequest` — the cap is consumed before the body is even parsed, so a malformed request still spends an allowance. `consumeRateLimit` throws an `ORPCError`, which only the oRPC handler knows how to serialize, so this raw route catches it and answers 429 itself.
- `packages/api/src/assistant/handler.ts › chatRequestSchema.locale` — the locale is a BCP-47 tag the client supplies (the server cannot infer it) and it is interpolated into the system prompt, so it cannot be free text: a multiline value would let a caller append their own rules. Hence the `LOCALE` regex.
- `packages/api/src/assistant/handler.ts › replayableHistory` — history always comes from the database, never from the posted transcript: `useChat` posts the whole conversation including assistant tool and step parts, and this route reads only the last message, so earlier entries are accepted unexamined.
- `packages/api/src/assistant/handler.ts › answerId` — the answer's row id is minted before it streams, so the client holds the id the table does and a regenerate can name the turn exactly, rather than guessing from the transcript's shape (which drifts the moment a turn is stopped) or matching on text (which collides when the same question is asked twice). Only the trailing turn can be redone; anything else appends.
- `packages/api/src/assistant/turn.ts › answerableParts` — a tool call the stream never resolved cannot be replayed: `convertToModelMessages` emits its `tool-call` with no matching `tool-result`, which an OpenAI-compatible endpoint rejects, poisoning every later turn in the conversation. Unresolved tool parts are therefore dropped before storage.
- `packages/api/src/assistant/turn.ts › isStorableOutcome` — `outcome.status` cannot tell whether a run failed, because a provider failure mid-answer still ends `completed` once the trailing `finish` chunk overwrites the outcome; the reported `finishReason` is the signal, and a run that reported none never finished. Only `error` marks a failure: `other` is what the OpenAI-compatible mapper returns for any `finish_reason` it does not recognise (Together's `eos` for a finished answer lands there), so refusing it would silently discard every turn on such an endpoint. A `length`-capped answer is still stored, because the reader saw that text, while `hasContent` exists because a stopped stream still emits a `step-start` marker and counting parts alone would store a turn holding nothing.
- `packages/api/src/assistant/conversation.ts › appendTurn` — the conversation row is updated _first_: at READ COMMITTED two concurrent turns would otherwise read the same `MAX(ordinal)` and one would lose to the unique index, and the write lock that update takes is what serializes them. The regenerate delete is scoped by id rather than by position, because the caller verified _those_ rows before the answer streamed and a turn committed from another tab meanwhile would otherwise be the one deleted; wrong ids are a no-op.
- `packages/api/src/assistant/provider.ts › isAssistantConfigured` — the API key is optional because a local runtime (Ollama, LM Studio) has none. Base URL and model are not defaulted: defaulting either would make an unconfigured instance look connected.
- `packages/api/src/assistant/tools.ts › decimalAmount` — amounts leave as decimal strings beside their currency. A model asked to divide by 100 itself does it for some rows of a list and not others, presenting a €120 budget as €12,000; a string rather than a number, because that is a figure to repeat, not to compute with, and JSON floats reintroduce the rounding the integer minor-unit model exists to avoid.
- `packages/api/src/assistant/tools.ts › get_accounts_overview` — `budget.getAccounts` carries IBANs because the interface shows them. No tool takes one as input and this one strips them, so they never reach the model provider and never land in the stored transcript that replays to it every turn.
- `packages/api/src/assistant/tools.ts › assistantTools` / `ASSISTANT_TOOL_NAMES` — each tool calls the very procedure the interface calls, through a server-side router client, so an answer here and a chart in Budget cannot disagree. The factory is checked with `satisfies Record<AssistantToolName, Tool>`, and `apps/web/src/pages/home/model/tool-labels.ts`, `tool-details.ts` and `components/assistant/assistant-tool-call.tsx` are checked against the same union, so a new tool cannot ship untranslated or without an icon.
- `packages/api/src/assistant/ui.ts › promptLibrary` / `ADDITIONAL_RULES` — Zod key order is the positional argument order the model writes in openui-lang, so each component's `props` object is ordered by importance rather than by name and the `sort-keys` disables are load-bearing. `@openuidev/lang-core`'s prompt generator also always appends its own stock "tables for comparisons, forms for input" rule, which is why the first entry of `ADDITIONAL_RULES` comes after it and names what actually exists.
- `packages/api/src/routers/assistant.ts › answerPartSchema` — validates `UIMessage["parts"]` only as far as its readers reach (`hasContent` reads `text`; `convertToModelMessages` reads a tool part's id and state), so a crafted part can neither crash the handler nor be stored as a call that replays with no result. `saveTurn` charges the same `AI_CHAT_RATE_LIMIT` allowance as a server question: the browser model cost nothing, but the two rows a turn writes still do.
